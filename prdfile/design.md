# 房东多房源房间租金视图：设计草案

## 1. 结论

当前模型不能直接可靠支持目标场景，但可以增量演进，不需要推翻现有银行流水与账本能力。

当前交付采用“多房产工作台、单房间完整链路验收”：数据库、领域对象、服务接口和房子视角都按多房产/多房间建立稳定主键与所有权边界；房子、房间、租客三个列表直接采用可扩展形态，但收租分配与详情链路当前只准备一个房间的验收数据。不使用硬编码唯一房产、唯一房间或缺少 `property_id` / `room_id` 的单例模型。

可复用的部分：

- 登录用户隔离与 EUR 账本约束。
- 月度应收、有效/作废状态、部分支付和逾期计算。
- 一笔流水多条 `payment_allocations` 的结构基础。
- 有效分配与现金收款共同投影 `paid_amount_cents` 的账本规则。
- 付款人身份关系、可逆操作与幂等键。

必须升级的部分：

- 把房产、房间、入住/租约、租客从 `tenants` 单表中拆开。
- 把“房间当月总租金”与“每位租客当月责任”建成可校验的两层账务事实。
- 允许付款人与债务责任人不同，并允许一笔款覆盖多个责任明细。
- 用稳定主键和账单快照支持房产、房间、租客聚合，不能继续依赖房间名称和地址文本。

## 2. 为什么当前模型不够

| 场景 | 当前能力 | 结论 |
| --- | --- | --- |
| 房东拥有多个房产 | 只有 `tenants.property_hint` 文本 | 名称可展示，不能保证实体唯一性、改名兼容或稳定聚合 |
| 房产包含多个房间 | 房间信息重复存于每个租客 | 无房间主键，无法可靠统计房间数或房间状态 |
| 一个房间多人同住 | 可把多个租客填成相同房间文本 | 数据库不认识它们属于同一个房间，可能重复计算房间租金 |
| 房间总租金 EUR 1,000 | 只有每个租客自己的 `monthly_rent_cents` | 无法表达 1,000 是房间总额，以及个人份额之和必须等于 1,000 |
| 甲替乙付款 | 付款身份和租客已有初步分离 | 分配服务禁止一笔流水跨多个租客，不能准确覆盖两人的责任 |
| 房产/房间/租客切换 | Dashboard 只按租客账单聚合 | 全局金额可算，房产/房间金额和未缴满房间数不可稳定计算 |
| 换房或租金变更历史 | 直接修改租客记录上的房间和月租 | 新值会失去合同语义，历史账单没有房间/合同快照 |

## 3. 推荐领域模型

```text
Landlord(User)
  └─ Property 1:N Room
                    └─ TenancyAgreement 1:N AgreementParty N:1 Tenant
                                         └─ monthly RentCharge
                                              └─ RentLiability N:1 Tenant

PaymentTransaction (实际付款人/银行流水)
  └─ PaymentAllocation N:1 RentLiability (款项覆盖谁的哪笔责任)
```

### 3.1 实体边界

#### Property

房东管理和统计的房产实体。至少包含 `id`、`user_id`、名称、地址、状态。名称可以改，聚合始终使用 ID。

#### Room

可出租的最小物理空间，归属一套 Property。至少包含 `id`、`user_id`、`property_id`、房号/名称、状态。

#### Tenant

只保存人的档案、联系方式和别名。月租、租期、应缴日和房间不再属于 Tenant 本身。

#### TenancyAgreement

房间在一段时间内的计费合同/租约，保存房间、起止日期、月度总租金、币种、应缴日和状态。根据工作簿证据，默认约束为同一房间在同一时段只有一份有效租约，一份租约可以包含多位参与人。本期只按整月生成应收，不计算月中天数比例。

#### AgreementParty

租约与租客之间的多对多关系，表达谁在此租约中居住。工作簿已经证明多人同住既有等分也有不等分，因此个人责任不能只保存人数或固定均分；可以在关系/条款层保存默认金额或比例，生成月度责任时固化为金额。底层可保留参与人独立起止日期，但本期不据此执行月中加入、退出、换人或按天折算。

#### RentCharge

所选月份内房间/租约的总应收事实。生成时快照 `property_id`、`room_id`、`agreement_id`、月份、总额、币种、应缴日和关键显示名称。后续改名、换房、调租不静默改变历史。

#### RentLiability

`RentCharge` 下的租客责任明细，所有明细的应收之和必须等于房间总应收。租客维度的“未交”应从这里计算。可以通过扩展现有 `rent_obligations` 承担这个角色，减少账本重写。

#### PaymentTransaction / PaymentAllocation

`PaymentTransaction` 记录实际谁付了钱；`PaymentAllocation` 记录这笔钱覆盖哪条 `RentLiability`。二者不得混为一谈。因此甲支付 EUR 1,000 可以分配 EUR 500 给甲的责任、EUR 500 给乙的责任。

### 3.2 推荐的最小迁移形态

为了保留现有账本和作废审计，推荐：

1. 新增 `properties`、`rooms`、`tenancy_agreements`、`agreement_parties`、`rent_charges`。
2. 保留 `tenants` 作为人员档案；旧租金/租期/房间字段进入兼容期，不再作为新账单的唯一事实来源。
3. 将现有 `rent_obligations` 演进为个人责任行，新增 `rent_charge_id`、合同与房间快照引用；旧账单保持原 ID 与付款关联。
4. 放开一笔流水跨多个租客责任分配的服务限制；`matched_tenant_id` 仅在目标租客唯一时保留，跨租客时为 NULL 或标记多目标。
5. 现金收款最终走同一付款与分配合同，避免银行支持代付而现金不支持。

不推荐只给 `tenants` 增加 `property_id` 和 `room_id`：这能做简单分组，却仍然无法表达房间总租金、多人责任、换房历史和共同付款。

## 4. 账务不变量

- 房间月应收：`RentCharge.expected_amount_cents`。
- 个人责任合计：同一 `RentCharge` 下有效 `RentLiability.expected_amount_cents` 之和必须等于房间月应收。
- 个人已覆盖：分配到该责任行的有效银行分配与有效现金分配之和。
- 房间已收：该房间当月所有有效个人责任的已覆盖之和，最大不超过房间应收；超付留在未分配余额或进入人工处理。
- 未收：`max(应收 - 已覆盖, 0)`。
- “未缴满房间”：所选账单月份下，房间有效总应收大于 0 且房间未收大于 0。
- “已交满房间”：所选账单月份下，房间有效总应收大于 0 且房间未收等于 0。
- “总房间”：所选月份内属于该房产且有效可出租的全部房间，包括没有当月应收的空置房。空置房不进入已交满或未交满，所以三者不构成强制加和关系。
- “空置”：房间在所选月份内没有有效租约/入住关系。不能仅以缺少 `RentCharge` 判断空置；若存在有效租约但账单缺失，应标记为“待处理”并暴露数据异常。
- 房产收缴率：房产当月有效租金已收除以应收；应收为 0 时显示 `—`，不显示 0% 或 100%。
- 房产和全局总额只能从同一组责任事实向上聚合，不分别维护可漂移的统计表。
- 付款到账月份与租金所属月份继续分开；房子、房间、租客视角和经营净额中的租金收入均由所选账单月份驱动，补交或提前支付按其覆盖的 `RentCharge.period_month` 归集。
- 作废的账单、责任与分配不计入有效汇总；历史更正通过调整/作废留痕，不原地覆盖已确认事实。

## 5. 示例：两人同住，一人全付

假设 9 月房间 A-01 总租金为 EUR 1,000，产品选择明确个人责任：甲 EUR 500，乙 EUR 500。

甲产生一笔 EUR 1,000 银行流水：

| 事实 | 甲 | 乙 | 房间 A-01 |
| --- | ---: | ---: | ---: |
| 应付责任 | 500 | 500 | 1,000 |
| 此流水分配 | 500 | 500 | 1,000 |
| 未付责任 | 0 | 0 | 0 |
| 实际从本人账户支付 | 1,000 | 0 | 1,000 |

这时：

- 房间是“已缴满”。
- 甲、乙都“不欠租”。
- 付款来源仍清楚显示“甲支付 EUR 1,000，其中替乙覆盖 EUR 500”。
- 如果产品还要显示“谁本人没转账”，应另列“本人支付”字段，不能把它误叫成欠租。

这个例子不是纯理论假设：工作簿的匿名聚合中有 6 个同类房间月份——某一责任行记录了整个房间的实收、同房另一责任行实收为零，但房间总实收恰好等于房间总应收。现有表格可以靠房间合计看出已缴满，却无法可靠说明付款如何覆盖另一人的责任；新系统需要用分配明细补上这条审计链。

### 5.1 场景合同

以下金额均为 EUR，状态按所选租金月份计算。标记“扩展合同”的场景用于约束底层数据结构和历史一致性，不扩大当前单房间 MVP 的页面操作范围。

| 场景 | 输入事实 | 必须产生的账务结果 | 视图与操作结果 | 本期范围 |
| --- | --- | --- | --- | --- |
| 单人足额支付 | 房间应收 1,000；甲责任 1,000；付款 1,000 | 甲已覆盖 1,000，房间未收 0 | 房间与甲均已交满；付款来源为甲 | 完整验收 |
| 多人不等分、尚未支付 | 房间应收 1,000；甲责任 600，乙责任 400 | 责任合计必须等于 1,000；房间未收 1,000 | 房间未缴；租客视角显示两条独立责任 | 完整验收 |
| 一人替同房全部支付 | 上述 600/400 责任；甲付款 1,000 | 自动分配甲 600、乙 400；房间未收 0 | 两人均已结清；乙显示“已结清（他人代付）”，不催缴 | 完整验收 |
| 部分代付待确认 | 上述 600/400 责任；甲付款 800 | 自动覆盖甲 600；其余 200 保持未分配，未确认前不得覆盖乙 | 房间已覆盖 600、未收 400；展示乙责任供人工确认 | 完整验收 |
| 部分代付人工确认 | 延续上一场景，人工确认将 200 分配给乙 | 甲已覆盖 600，乙已覆盖 200、未付 200 | 房间为部分缴纳；仅乙进入催缴候选 | 完整验收 |
| 超付 | 上述 600/400 责任；甲付款 1,200 | 最多分配 1,000；200 保持流水未分配，不得形成负未收 | 房间已交满；另显示 200 待处理余额 | 完整验收 |
| 单人部分支付 | 甲责任 1,000；付款 300 | 已覆盖 300、未付 700 | 房间与甲为部分缴纳；到期后转为对应逾期展示 | 完整验收 |
| 空置房 | 所选月份无有效租约/入住关系 | 不生成租金应收，不计已交满或未交满 | 计入总房间；金额、收缴率和到期日显示 `—`；排序最后 | 查询验收 |
| 有租约但缺账务事实 | 所选月份有有效租约，但缺少房间应收或责任合计不一致 | 不猜测金额或把房间当空置 | 标记 `needs_review` 并排在最前 | 查询验收 |
| 空缺或冲突身份 | 迁移候选存在应收但没有唯一租客，或合并姓名无法唯一解析 | 不自动建立责任或分配 | 进入迁移预览异常；当前无初始化流程时只显示可解释空状态 | 扩展合同 |
| 作废或撤销分配 | 已交满房间的一批分配被整批撤销/作废 | 相关责任、房间和房产汇总在同一事务后重新投影 | 状态按剩余有效分配降级；保留完整审计记录 | 完整验收 |
| 房产公共支出 | 支出仅有 `property_id`，没有 `room_id` | 计入房产及全局支出和经营净额 | 不出现在任何房间详情，不分摊给房间 | 完整验收 |
| 房间支出 | 支出同时有 `property_id` 和 `room_id` | 计入该房间、所属房产和全局经营净额 | 不改变租金已收、未收或缴满状态 | 完整验收 |
| 同一租客跨房间 | 同一租客同月尝试加入两个房间 | 保存第二个房间计划时锁定租客并返回 `ErrTenantRoomMonthConflict`；目标月份前已结束的历史计划不冲突 | 页面提示租客已在其他房间入住；有效首页数据最多一行 | 完整验收 |
| 整月换房或退租 | 新月份起新租约生效或旧租约结束 | 旧月份账单快照不改写；新月份按新关系生成或显示空置 | 历史月份仍落在原房产/房间；月中折算不在本期 | 扩展合同 |
| 多房产排序 | 一套房含 `needs_review` 房间，另一套仅有逾期/已交满房间 | 房产行状态取所属房间最严重状态 | `needs_review` 房产优先；同级按未收降序、名称稳定排序 | 查询验收 |

这些场景同时约束四级汇总：个人责任有效覆盖额之和等于房间已收，房间已收之和等于房产已收，房产已收之和等于全局已收；未分配余额、押金、支出和待确认其他收入都不得混入该等式。

## 6. 查询与界面设计

### 6.0 当前 MVP 切片

- 月度工作台是固定入口，顶部月份与全局汇总保持不变，主体通过 `view=properties|rooms|tenants` 切换房子、房间和租客视角。
- 房子视角从本期开始支持多套房产，每套房一行，展示总房间数、已交满房间数、未交满房间数、应收、已收、未收、收缴率、当月支出和经营净额；点击后切换到携带该 `property_id` 的房间视角。
- 房间列表沿用统一月份选择器，每行展示房间标识、当月入住人数、应收、已覆盖、未收和状态；列表与详情共用相同的 `RentCharge` / `RentLiability` 汇总查询。
- 房间列表默认展示空置房；空置行的应收、已收、未收、收缴率和到期日显示 `—`，仍允许进入房间详情查看资料及支出。
- 租客视角以 `RentLiability` 为行粒度，即“租客 × 房间 × 租金月份”一行；展示应付、已覆盖、未付、状态、所在房间和实际付款来源，并保留单人/批量催缴入口。同一租客同月最多一行，计划保存时拒绝跨房间重叠。
- 三个视角默认统一使用“需要处理的项目优先”排序，状态优先级为 `needs_review -> overdue -> partial -> open -> paid -> vacant`。房子视角用房产内最严重的房间状态作为房产行的状态排序键；同级先按未收金额降序，再按房产名称稳定排序。房间和租客视角同级先按未收金额降序，再按到期日和名称稳定排序。
- 点击列表行进入房间详情页，详情路由显式携带 `room_id`，查询同时使用 `user_id`、`property_id`、`room_id` 和账单月份做所有权限定。
- 房产、房间、租约参与人和责任条款由用户在系统外自行初始化；当前页面不提供创建/迁移向导，也不根据旧文本字段自动推断关系。
- 列表为空、详情目标不存在或当月没有责任时分别返回可解释空状态；不能偷偷回退到任意第一条房间或旧 `room_label` 数据。
- 详情页展示房间月总应收、已覆盖、未收、状态，以及房内各租客责任与付款来源。
- 单房间不是单租客简化版：必须支持多位参与人、不等分责任，以及一笔付款覆盖当前房间内多条责任。
- “只实现一个房间”只限制本期完整收租链路的验收数据，不限制房子视角的多房产行数，也不把房间列表或查询写成单例。
- 三个视角复用同一 `RentCharge` / `RentLiability` 事实逐层聚合，增加房产或房间数据不会改变历史账单和付款分配。

### 6.1 页面结构

推荐保留一个统一的“月度收租工作台”，顶部月份选择器作为全页上下文：

1. 顶部固定显示全局卡片：总应收、已覆盖、未收、收缴率、未缴满房间数、待处理流水数。
2. 下方用分段切换：`房子` / `房间` / `租客`。默认进入房子视图。
3. 支持自然下钻：点击房产进入该房产的房间列表；点击房间展开/进入租客责任与付款明细。
4. 所有筛选都保留 `period`，并通过 URL 查询参数保存 `view`、`property_id`、`room_id`、状态、搜索和分页。

单独做多个互不相干的 Dashboard 容易造成口径漂移；只做树状页面又不利于直接查欠租租客。因此采用“统一月份与总览 + 房子/房间/租客视角切换 + 房间详情下钻”的组合。视角用 URL 查询参数保存，例如 `/rent-dashboard?period=2026-09&view=properties`；从房子下钻后使用 `/rent-dashboard?period=2026-09&view=rooms&property_id=...`，刷新和返回时不丢失上下文。

### 6.2 各维度最小字段

| 维度 | 主行 | 指标/字段 |
| --- | --- | --- |
| 全局 | 所选月份 | 应收、已覆盖、未收、收缴率、有账单房间数、未缴满房间数、欠款责任人数、待处理流水 |
| 房产 | 每套房产 | 总房间数、已交满房间数、未交满房间数、应收、已收、未收、收缴率、当月支出、经营净额 |
| 房间 | 每个房间 | 房产、房间、当月租客、应收、已覆盖、未收、状态、到期日 |
| 租客 | 每条月度责任（租客 × 房间 × 月份） | 房产、房间、租客、个人责任、已被覆盖、未付、状态、实际付款来源摘要 |

### 6.3 状态定义

- 房间 `paid`：房间未收为 0。
- 房间 `partial`：已覆盖大于 0 且未收大于 0。
- 房间 `open/overdue`：未覆盖且按 Dublin 日期判断是否逾期。
- 房间 `vacant`：所选月份没有有效租约/入住关系；不参与已交满、未交满及租金金额汇总。
- 房间 `needs_review`：所选月份存在有效租约，但应收或责任事实缺失/不一致；不得降级显示为空置。
- 租客“欠租”：个人责任未付大于 0；与实际付款人是不是本人无关。
- 付款人状态：只作为解释性信息展示，例如“本人支付”“由甲代付”，不参与欠租判断。
- 催缴候选只包含个人责任未覆盖金额大于 0 的租客；责任已被他人完整覆盖时显示“已结清（他人代付）”，不催缴。

## 7. 匹配与分配建议

- 自动匹配继续保守：付款身份映射到多个租客时，不自动猜测分摊比例。
- 人工确认时可选择“按同一房间当前未付责任自动铺满”，提交前预览每条分配。
- 足额覆盖规则：付款身份唯一、目标房间和月份明确、币种一致，且付款可覆盖房间当月全部未付责任时，先覆盖付款人自己的未付责任，再按稳定责任顺序铺满同房其他责任；超出本人责任的金额标记为代付。该场景自动确认，不再逐人询问。
- 若付款超过房间全部未付责任，只把房间未付部分计入租金；超出部分保留为流水未分配余额或待处理，不得制造负未收。
- 部分代付规则：付款超过付款人本人未付责任但不足以结清房间时，只自动覆盖付款人本人；剩余金额保持未分配，列出同房其他未付责任供人工选择。确认动作必须原子写入所选分配并保留代付来源。
- 底层账本允许同一用户、同一币种下的一笔付款关联多个责任行，不在数据库或领域模型中增加“所有责任必须属于同一房间”的永久约束。
- 当前 MVP 的产品入口只允许选择当前房间内的责任；跨房间选择、预览、确认和自动规则全部后置。本期只验证底层关联不会阻碍未来扩展，不实现或测试实际跨房间分配流程。
- 分配总额不得超过流水可用余额，也不得超过各责任剩余余额。
- 撤销继续以完整操作批次留痕，并重新投影所有受影响责任与房间状态。

## 8. 兼容与迁移

- 本任务明确升级旧 V1 的两个边界：正式引入独立 `Property` / `Room` 实体，并允许一笔付款分配到同房多位租客的责任。
- 旧 V1 的跨房间付款、月中换房/退租折算和自动初始化仍保持后置；“底层不限制跨房间”只代表关联模型可扩展，不代表本期开放该操作。
- 现有租客按 `user_id` 隔离；迁移为每个用户建立房产、房间和租约记录。
- 可用规范化后的 `property_hint + room_address + room_label` 生成分组候选，但必须输出冲突/缺失报告；不能仅凭模糊文本静默合并历史房间。
- 缺少房产信息的旧租客进入“待归类房产”，不阻塞账务查看。
- 现有 `rent_obligations` 和已确认分配保留 ID；通过新增引用或快照字段挂接，禁止删除后重建。
- 历史账单的应收、实收和状态不因新租约数据而重算；新模型从明确切换月份开始生成未来账单。
- 在切换期提供双读核对：旧全局汇总应与新模型全局汇总一致，再启用新维度页面。

### 8.1 工作簿迁移约束

- 4 个同构页签各自维护稳定房间集合和月度汇总，迁移候选可先按“页签 -> 房产、房间号 -> 房间”建立映射，但必须由用户预览确认，不能把页签名称或房间文本直接当永久主键。
- 8 个重复月份块证明表格把主数据和月度事实混在一起；导入时要分别落为房间/入住关系、月度责任、付款/分配和费用，不复制这种宽表结构。
- 多人房间按多行保存，每行有个人应收；导入时按房间与月份先形成房间总应收，再保留每行个人责任金额。
- 多人房间在日期完整时共享合同/入住日期，可迁移为共同租约；日期缺失或冲突时进入人工确认，不能据邻行自动补齐。
- 合并姓名文本、缺少姓名但有应收、超收、跨人代付和房间合计不平等情况全部进入预览异常队列，不自动修复。
- 疑似押金/保证金的独立金额列不能并入租金实收；导入映射确认前只作为待分类金额展示。
- 部分标题为损坏公式，导入器必须读取已确认模板版本与列位置，并验证内容类型；不允许依据当前显示标题猜列。
- 原始工作簿只作为用户控制的导入源，系统记录导入批次与匿名校验结果；不把原文件内容写入日志、规划文档或长期记忆。

## 9. 费用与经营结余边界

工作簿把租金实收、月度支出和盈余放在同一房产页签中，说明房东最终可能需要经营视角。但这三类事实必须分层：

- 收租状态只由房间/租客的租金应收与有效租金分配决定。
- 押金继续作为独立用途，不计入租金实收。
- 支出至少要能归属房东和房产；是否必须归属房间由费用场景决定。
- 经营净额公式确定为：`已收租金 + 已确认其他收入 - 有效支出`。押金、未分配流水、待确认收入以及作废记录不进入公式，也不能反向改变“房间是否缴满”。
- 经营净额中的已收租金使用所选月份责任的有效覆盖额，不使用付款流水的自然到账月份；到账日期保留在付款明细和未来现金流视角中。
- 用户已确认单房间 MVP 保留支出能力：现有 `manual_expenses` 继续作为支出事实，新增稳定的 `property_id` 与可选 `room_id`；旧 `room_hint` / `tenant_hint` 仅用于兼容显示和迁移，不再作为聚合键。
- 房子视角汇总直接关联该 `property_id` 的有效支出；房间级支出因同时携带 `property_id`，自然向上计入所属房产。缺少稳定房产归属的旧支出不猜测归类。
- 仅关联 `property_id`、未关联 `room_id` 的支出定义为房产公共支出：只进入房子级和全局支出/经营净额，不复制、平均或按比例分摊到房间。
- 其他收入同样需要稳定 `property_id` 才能进入某套房的经营净额；无法归属的已确认其他收入只进入全局待归类汇总，不按付款人或备注猜测到房产。
- 房子视角展示当月支出和经营净额，但收缴率仍只由租金应收与有效租金分配计算。
- 房间详情页只展示明确关联该 `room_id` 的所选月份支出合计和经营净额；房产公共支出不展示、不分摊。经营净额与租金收缴状态分开，不能因为支出而把已缴满房间改成未缴。

### 9.1 发票附件扩展边界

推荐按一笔支出对应多份附件设计，而不是在 `manual_expenses` 上增加单个 `invoice_url`：

```text
Expense 1:N ExpenseAttachment
```

附件元数据至少预留 `id`、`user_id`、`expense_id`、原始文件名、MIME 类型、大小、对象存储键、内容哈希、上传者、创建时间和记录状态。数据库只保存元数据和存储键，不保存公开 URL；下载必须重新校验当前用户对支出的所有权。

实际文件上传已确认后置到下一阶段。本期不创建假上传入口，也不把描述字段或备注字段当文件地址使用；支出主表的稳定主键、所有权和房间归属必须足以让下一阶段安全新增一对多附件表。

## 10. 风险与回滚

- 最大产品风险是没有定义共同租金下的个人责任，却要求判断“哪个租客没交”；这两个要求逻辑上冲突。
- 最大迁移风险是把相同房间文本误合并，或让历史账单因新关系变化而漂移。
- 最大账本风险是放开跨租客分配后，撤销只更新一个租客/账单。实现时必须锁定并重算全部目标责任。
- 数据库迁移采用只增不删；功能开关控制新账单生成和新 Dashboard。回滚时关闭新入口，旧账单及旧页面仍可读。

## 11. 已确认产品决策

1. 三个视角均采用“需要处理的项目优先”默认排序：待处理/数据异常、已逾期、部分缴纳、未到期未缴、已交满、空置。
2. 房子行以房产内最严重的房间状态作为主排序键；同级按未收金额降序、房产名称稳定排序。房间和租客行同级按未收金额降序，再按到期日与名称稳定排序。
