# 房东多房源房间租金视图

## Goal

把当前以租客为核心的 RentOps 数据模型演进为可支持多房产、多房间、多人同住和代付的房东账务模型；当前 MVP 提供支持多套房记录的房子/房间/租客月度工作台，但只用一个房间完整验收收租闭环。后续增加更多房间数据或业务链路时，不重构账本核心。

本阶段只做需求澄清、现有模型适配性评估和方案设计，不开始实现。

## User Scenarios

- 一个房东拥有多套房产，每套房产有多个房间。
- 一个房间在某个时间段可以没有租客、只有一个租客，或有多个租客共同居住。
- 一个房间当月总租金可以是 EUR 1,000；存在一位租客替另一位租客支付全部或部分租金的情况。
- 房东可以查看所选月份全部房产的总应收、总实收和未收。
- 房东可以切换到房产维度，查看每套房产的总房间数、已交满房间数、未交满房间数、应收、已收、未收、收缴率、当月支出和经营净额。
- 房东可以切换到房间维度，查看哪些房间未缴满及其差额。
- 房东可以切换到租客维度，查看哪些租客仍有应付责任未完成。

## Confirmed Facts

- 使用者仍是房东，所有统计均受当前登录用户的数据隔离约束。
- 时间口径沿用产品现有约定：由界面当前选择的账单月份驱动，不固定取系统当前月。
- “同住关系”“租金责任”“实际付款人”“付款分配到哪笔应收”需要作为不同概念评估，不能仅凭银行付款人姓名判断谁已缴费。
- 当前仓库已经有租客、月度应收、银行流水分配、现金收款和催缴能力。
- 当前 `tenants` 同时承载租客资料、月租、起止日期、应缴日、房间标签、房屋地址和房产提示；没有独立的 `properties`、`rooms`、`tenancies/contracts` 表。
- 当前每月应收的唯一粒度是 `user_id + tenant_id + period_month`，由租客记录上的 `monthly_rent_cents` 直接生成，因此本质上是“每租客每月一张账单”，不是“每房间总账 + 租客责任明细”。
- 当前 `tenant_payers` 已把银行付款身份与租客档案部分拆开，数据库也允许同一付款身份出现在多个租客关系中；但自动匹配会把这种情况判为歧义。
- 当前 `payment_allocations` 已允许一笔流水产生多条分配，但服务层明确拒绝这些分配跨越多个租客；`payment_transactions.matched_tenant_id` 也是单值。
- 当前 Dashboard 的总应收、实收和未收来自租客月账单求和，列表和筛选均以租客为主；没有可依赖的房产或房间主键，无法稳定按房产/房间聚合或计算“未缴满房间数”。
- 旧 V1 产品边界明确把独立房间、换房历史和跨租客拆分后置；本任务是对该边界的有意升级。
- 早期架构设计曾提出 `Property`、`Room`、`Tenancy`、`Contract`、`ContractTermSnapshot` 和 `ReceivableInvoice`，方向与本需求一致，但尚未落到当前数据库和代码。
- 用户提供的本地收租工作簿已按只读、匿名化方式分析；原始姓名、地址、付款备注和逐户金额不进入本任务文档或长期记忆。
- 工作簿有 4 个同构页签，每个页签各含 8 个按月重复的数据块；页签内房间号集合跨月稳定，而入住人组合会变化。这支持“页签/分组近似房产、房间为稳定实体、入住关系带时间”的模型。
- 工作簿每月约有 25 个稳定房间键和 40 个租客责任行。匿名统计中有 112 个“同房间同月多行”组合，其中 101 个组合的个人应收相等、11 个不等，说明个人责任必须支持明确金额而不能固定均分。
- 工作簿中有 6 个清晰场景：同一房间一行实收覆盖房间全部应收、另一行实收为零，而房间合计刚好缴满。这直接验证了“实际付款人”与“被覆盖的个人责任”必须分离。
- 工作簿的多人房间在合同/入住日期完整时使用相同日期，因此默认模型采用“一份房间租约包含多位参与人”；参与人保留可选独立起止日期作为未来扩展字段，但本期只处理整月责任。
- 工作簿也存在少量有应收但缺少姓名、合并姓名文本、个人实收高于/低于个人应收、房间超收等不完整或需解释数据，迁移时必须进入待确认流程，不能自动猜测。
- 工作簿同时维护月度支出与盈余，并含疑似押金/保证金的独立金额、付款方式和日期列；由于相关标题公式已经损坏，具体语义必须在导入预览中由用户确认。这些金额必须与租金应收/缴满状态分账。用户已确认本期房子视角展示支出与经营净额。
- 工作簿部分列标题公式已出现 `#REF!`，说明未来导入不能依赖活动单元格公式或模糊列名，必须使用版本化模板、显式列映射与导入预览校验。
- 用户确认当前交付范围只实现一个房间，但底层数据结构必须支持未来扩展到多房产、多房间。
- 用户确认单房间 MVP 必须完整支持多人同住、每人不同应付金额，以及一人替其他租客支付全部或部分租金。
- 用户确认单房间 MVP 保留现有支出能力；后续需要为支出上传发票，因此当前支出实体和归属设计不得阻碍一笔支出关联多份凭证。
- 用户确认发票上传、查看和删除不属于当前 MVP，在下一阶段单独实现；当前只保留清晰的一对多附件扩展边界。
- 用户确认当前 MVP 不实现房产、房间、租约参与人和责任金额的初始化流程；初始数据由用户自行准备，系统只负责读取和运营。
- 用户确认租客“是否欠租”按个人责任的未覆盖金额判断；本人是否实际转账单独展示，不参与欠租或催缴判断。
- 用户确认：当一笔付款能够覆盖当前房间所选月份的全部未付租金时，超过付款人本人责任的部分默认视为替同房其他租客代付，系统自动覆盖房间内各责任，无需逐人确认。
- 用户确认：付款超过付款人本人未付责任、但不足以结清整个房间时，不自动决定替谁支付；超过本人责任的剩余金额进入人工分配确认。
- 页面入口是房间列表页，当前 MVP 只展示一个房间；点击房间进入详情页。`room_id` 属于详情页和后端查询合同，不代表系统只有一个固定房间页面。
- 用户确认房间列表的每一行直接展示所选月份的应收、已收、未收和缴费状态，并可点击进入详情。
- 用户确认月度工作台支持房子、房间与租客三个视角切换；房东可能拥有多套房子，房子必须是独立汇总粒度，不只是房间上的文本筛选条件。
- 用户确认月度工作台首次进入时默认显示房子视角；房东先查看多套房的总体收缴情况，再按需下钻房间或切换到租客。
- 用户确认房子视角每套房展示总房间、已交满、未交满、应收、已收、未收和收缴率。
- 用户确认没有当月租金应收的空置房计入总房间，但不计入已交满或未交满；因此总房间数不要求等于已交满与未交满之和。
- 用户确认房子视角同时展示当月支出和经营净额；支出与租金收缴事实保持分账。
- 用户确认经营净额公式为“已收租金 + 已确认其他收入 - 有效支出”；押金、未分配流水和待确认收入不计入经营净额。
- 用户确认经营净额中的已收租金按租金所属月份归集，而不是按银行流水实际到账月份；晚到款会回填原租金月份的经营净额。
- 用户确认底层付款分配模型不写死“只能同房间”，保留未来一笔付款跨房间分配的扩展性；当前 MVP 的操作入口和验收仍仅覆盖当前房间。
- 用户确认房间视角默认展示空置房并标记为“空置”；空置房的应收、已收、未收和收缴率显示 `—`。
- 用户确认仅归属房产、没有指定房间的公共支出只进入房子级支出和经营净额，不展示或分摊到任何房间详情；房间详情仅统计明确关联该 `room_id` 的支出。
- 用户确认本期不考虑多人租约成员在月中加入、退出、换人或租金按天折算；本期责任按整月明确金额处理。
- 用户确认租客视角每一行表示“租客 × 房间 × 租金月份”的一条个人责任，不把同一租客在不同房间的责任合并成一行。
- 用户确认房子、房间和租客三个视角统一采用“需要处理的项目优先”默认排序：待处理/数据异常、已逾期、部分缴纳、未到期未缴、已交满、空置。
- 当前 `manual_expenses` 已有描述、类别、金额、币种、支出日期和付款方式，但房间/租客仅是文本提示，没有稳定的 `property_id` / `room_id`，也没有附件实体。

## Requirements

- 数据模型支持 Property -> Room 的一对多层级。
- 数据模型支持 Room <-> Tenant 随时间变化的多对多入住关系，并可保留历史。
- 当前 MVP 只需打通一个房间的完整业务链路，但房子列表、房间列表、详情和服务不得使用全局单例或删除 `property_id` / `room_id`；房子视角从一开始支持多套房记录。
- 房间详情页和服务显式使用 `room_id`；房间列表为空或详情目标不存在时显示明确空状态，不自动从 `room_label`、地址或姓名文本生成关系。
- 默认一间房同一时间对应一份有效租约，租约可包含多位参与人；每位参与人有独立责任，底层可保留独立生效区间，但本期计费只支持整月责任。
- 月度应收必须能稳定归属到房间、租约/入住关系和相关租客，不因后来换房、退租或改租金而改写历史。
- 多人同住时必须记录每位租客的明确应付金额；可以提供均分作为录入快捷方式，但允许不等分，且有效责任合计必须等于房间总租金。
- 付款人可以与租客本人不同；一笔付款可以在明确规则下覆盖同房租客的全部或部分应收。
- 当前 MVP 允许一笔付款分配到当前房间内多位租客的责任；分配前展示预览，提交后保留实际付款人与每条责任覆盖金额。
- 底层 `PaymentAllocation` 只关联付款与目标责任，不增加永久性的同房间数据库约束；跨房间如何选择和确认属于后续产品能力，本期不提供跨房间入口。
- 当付款人、房间、租金月份和币种均唯一且付款金额足以覆盖房间全部未付责任时，系统自动按责任剩余金额铺满；付款超过整个房间未付金额的部分不得计为租金，保留为未分配余额或进入待处理。
- 当付款金额只能部分覆盖同房其他租客时，系统最多自动覆盖付款人自己的剩余责任；其余金额保持未分配并展示同房未付责任供人工选择，确认后才记为代付。
- 所有层级使用同一套账务事实汇总，避免全局、房产、房间和租客视图出现口径不一致。
- 当前 MVP 提供房间列表页，以及所选房间在所选月份下的应收、实收、未收、缴费状态和租客责任详情。
- 房间列表由统一月份选择器驱动；每行至少展示房间标识、当月入住人数、应收、已覆盖、未收和状态。列表金额必须与详情页由同一账务事实聚合。
- 月度工作台使用同一个月份和顶部汇总，主体可切换 `房子视角`、`房间视角` 与 `租客视角`；切换只改变列表粒度，不改变金额口径。
- 月度工作台默认使用 `view=properties`；用户主动切换到房间或租客视角后，URL 保留所选视角和月份。
- 房子视角每套房一行，展示总房间数、已交满房间数、未交满房间数、应收、已收、未收、收缴率、当月支出和经营净额，并可下钻该房子的房间列表。
- 房子视角的总房间数统计该房产在所选月份内有效的全部可出租房间，包括没有当月应收的空置房；已交满与未交满只统计当月应收大于零的房间。
- 房子视角的应收、已收、未收和收缴率只汇总所选月份有效租金账务事实；空置房不贡献金额，支出不改变这些指标。
- 房子视角的当月支出按稳定 `property_id` 汇总，同时包含直接归属房产和归属该房产下任一房间的有效支出；经营净额作为独立指标，不反向改变收缴状态。
- 房子视角的经营净额为该房产范围内的“已收租金 + 已确认其他收入 - 有效支出”；押金、未分配流水、待确认收入、作废收入和作废支出不计入。其他收入必须有稳定的 `property_id` 才能进入某套房的经营净额。
- 经营净额中的租金收入按 `RentCharge.period_month` / 责任所属月份汇总，不按付款到账月份汇总；因此补交或提前支付的租金归入其对应租金月。
- 房间视角按房间聚合并支持进入详情；租客视角按“租客 × 房间 × 租金月份”的个人责任展示应付、已覆盖、未付、状态、所在房间和付款来源，并保留催缴操作。同一租客若未来在同月有多个房间责任，应显示多行。
- 房间视角默认列出所选范围内的全部有效房间，包括空置房。只有所选月份没有有效租约/入住关系的房间才标记为“空置”；有有效租约但应收事实缺失时标记为“待处理”，不能误标为空置。
- 空置房的应收、已收、未收、收缴率与到期日显示 `—`，不进入租金汇总、已交满或未交满计数；它仍可点击进入房间详情查看房间资料和支出。
- 三个视角的默认排序统一为 `needs_review -> overdue -> partial -> open -> paid -> vacant`。房子行以该房产下最严重的房间状态作为主排序键，同级按未收金额降序、房产名称稳定排序；房间和租客行同级按未收金额降序，再按到期日及名称稳定排序。筛选或分页不得改变该优先级语义。
- 当前 MVP 的租客明细至少显示个人责任、已覆盖金额、未付金额、状态和实际付款来源。
- 当他人已完整覆盖某位租客的责任时，该租客显示“已结清（他人代付）”；不得显示欠租，也不得进入催缴候选。
- 统计需正确处理部分支付、代付、超付、退款/作废及历史关系变更。
- 当前 MVP 保留支出新增、列表和所选月份汇总；支出正式关联 `property_id`，并可选关联 `room_id`。从房间详情页新增支出时默认关联该房间，但底层不把房间写死。
- 房间详情和房间经营净额只使用明确关联目标 `room_id` 的收入与支出；仅关联 `property_id` 的公共支出不展示、不分摊，也不计入任何房间经营净额。
- 房间经营净额与租金收缴状态分开计算：支出不能减少租金实收，也不能改变租客或房间是否缴满。
- 支出附件采用一对多扩展边界；当前 MVP 不实现实际文件上传、查看或删除。

## Out of Scope

- 租客自助门户。
- 多房东 SaaS 或团队权限体系重构。
- 多币种换汇；一期继续以 EUR 为唯一汇总币种。
- 空置率、收益率、租金趋势等高级经营分析，除非后续访谈明确纳入。
- 月中入住、月中退出、月中换人及租金按天折算；本期以整月责任为唯一计费粒度。
- 当前 MVP 不实现房产资料维护向导和跨房间付款分配；房子/房间列表与房产级汇总保留，完整收租链路的验收数据范围可以只有一个房间。
- 当前 MVP 不做整份工作簿的全量迁移；工作簿仅作为模型和测试场景证据。
- 当前 MVP 不实现发票文件上传、预览/下载、删除、存储和附件审计。
- 当前 MVP 不实现房产/房间创建表单、入住人选择向导、责任均分向导或旧租客文本自动合并。
