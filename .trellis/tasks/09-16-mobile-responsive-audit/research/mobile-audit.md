# 移动端适配审计报告

审计对象：https://bank.ddpl.top（生产库，`rentops-demo` 账号的真实数据，10 个租客）
方法：Playwright + Chromium 143 驱动真实浏览器，视口 375×667 / 390×844 / 768×1024
证据：`report.json`（溢出与根因元素）、`metrics.json`（触控目标 / 字号 / 列可达性）、`report-extra.json`（两个补充页）、`tile-index.json`（截图索引）
截图：`/tmp/mobile-audit/tiles/`（逐页按视口切片，2x）、`/tmp/mobile-audit/out/`（整页）

> 本报告的每一条结论都来自真实浏览器渲染。**审计前我曾静态推断「固定像素列宽必然导致横向溢出」，实测证明该推断是错的**——10 个页面 × 3 个视口，页面级横向溢出全部为 0（见「通过项」）。以下按实测修正。

## 结论摘要

| --- | --- |

## P0-1：侧边栏吃掉首屏 55%

375×667 实测（`/tenants`）：`.sidebar` 359 × 364px，`.content` 起始于 y=372。即在任何页面打开时，用户**必须先划过 372px 的重复导航**才能看到内容；`/billing` 首条数据出现在 y≈1292（约 2 个整屏），`/tenants` 首条数据在 y=959（约 1.4 屏）。

`@media (max-width: 980px)` 只把 `.app` 从两列改成单列（`main.go:2379`），侧边栏因此变成通栏区块堆在正文之上，而不是折叠。导航在页面间重复，且不是 sticky——滚下去就切不了页。

## P0-2：关键操作列默认在屏外，且滚到位后丢失行身份

横向滚动本身是设计选择（`.table-wrap{overflow-x:auto}`），但**把唯一的操作入口放在最右、且没有任何可见提示**（移动端不渲染滚动条，无渐变遮罩、无 sticky 列），等于相关页面在手机上退化成只读。

`/tenants` 是这个问题最硬的证据（DOM 实测，非截图推断）：

```
表宽 680px，容器可视宽 327px；滚动余量 353px
scroll = 0    : 列 0/1/2 可见（租客 付款人 租金），列 3/4/5/6 全部隐藏
scroll = max  : 列 0/1/2 全部隐藏，列 4/5/6 可见（房间 创建时间 操作）
```

姓名列占 x 0–78，操作列占 x 544–680，**两者相距 466px > 容器可视宽度 327px**——因此**不存在任何一个滚动位置能同时看到租客姓名与「详情/编辑」按钮**。而该页没有任何其它进入详情/编辑的入口（姓名列不是链接，点击整行只就地展开账单）。用户无法确认自己按的是哪一位租客的按钮。

同类问题：

| 页面 | 关键操作 | 需滑动 | 后果 |
| --- | --- | --- | --- |
| `/billing` | 关联并记住 / 归类拆分 / 无需匹配 / 撤销匹配 | **713px** | 该页全部主要操作不可见，流水页在手机上只能看不能处理 |
| `/tenants` | 详情 / 编辑 | 353px | 滚到位后行身份已丢失 |
| `/rent-dashboard` | 未收金额、状态 | 333/391px | 每行「还欠多少」不可见 |
| `/billing/payer/preview` | 确认此笔 | 卡片滚动 415px | 见 P0-4 |

## P0-3：金额列被视口截断成「看起来完整」的错误数字

`/billing` 第 3 列（屏幕最右）被右缘拦腰截断。DOM 实测（375px，scroll=0）：

```
col2 金额／余额   full=139px  visible=110px   *** SLICED ***
     渲染文本 "GBP 25.00已分配 GBP 0.00余款 GBP 25"
                                              ↑ 真值 GBP 25.00，末位被切掉
col6 用途／处理   full=320px  visible=0px     完全在屏外（全表最宽的一列）
```

截断后仍是语法完整的数字，且无省略号或淡出提示，**用户无法判断 `GBP 25` 是 25.00 还是 25.05**。同类渲染还有 `EUR 1800.0`、`已分配 EUR 700.`。

`/billing/payer/preview` 同样：截图实测金额列显示为 `E8`（`EUR 8…`）与 `G2`（`GBP 2…`），仅露出两位数。

这是财务页面上最不该出的问题类型：不是"看不到"，而是"看到一个不确定对不对的数"。横向滚几十 px 即可看全，但默认视图就是这样。

## P0-4：付款人预览页把整张卡片变成了横向滚动容器

全站做法是「只把表格包进 `.table-wrap`」。`/billing/payer/preview` 例外：它在 `@media(max-width:760px)` 下给 `main.card` 加了 `overflow-x:auto`（`transaction_previews.go:132`），于是横滑容器是**整个卡片**——DOM 实测 `scrollRange: 415px`、`containsHeading: true`、内边距 18px 一并滚动。横滑时页标题、说明文字与「返回流水」链接全部滚出视野。

该页还完全绕开 `workspacePageCSS`，自带一套 `:root{--canvas/--ink/--muted}` 配色，与全站的 `--surface/--foreground/--foreground-muted` 不是同一体系，视觉上像另一个应用。

## P1-3：列被挤压到逐字断行

- `/expenses` **类别列实测仅 52px**，「物业」被逐字断成两行（DOM 实测 2 个行盒）。
- `/tenants` **账单安排列实测 59px**，`每月 1 日 / 2026-07-01 至 2026-09-30` 断成 5 行。
- `/tenants` **创建时间列 55px**，未本地化的 ISO 时间戳 `2026-09-16T05:11:12Z` 断成 5 行（`2026 / -09- / 16T0 / 5:11 / :12Z`），完全不可读，却额外占一列宽并进一步撑高行。

CJK 允许逐字断行，所以这类列不会被"截断"，而是被"竖排"，比截断更难读。

## 通过项（明确无问题）

- **无页面级横向溢出**：10 个页面 × 3 个视口全部 `scrollWidth == clientWidth`。
- **宽表格正确包裹**：9 个页面的表格都在 `.table-wrap`（`overflow-x:auto`）内（唯一例外见 P0-4）。
- **移动端键盘类型正确**：金额 `inputmode="decimal"` ×4，日期 `type="month"` ×13 / `type="date"` ×8。
- **登录页**：375px 下布局干净，输入框与按钮均为通栏。
- **抽屉与展开行**：催缴抽屉、租客展开行在 390px 下均无横向溢出；展开子表无嵌套滚动陷阱（`innerScrollRange=0`）。
- **`/billing/revoke` 撤销预览页是全站手机端表现最好的页面**：单列布局、输入框通栏、零溢出、无滚动容器。仅控件高度 37–43px 略低于 44px。
- **`/cash-receipts/new` 与 `/cash-receipts/void`** 无横向滚动、无被挤出视口的内容。
- **逐张截图复核确认「无严重级问题」的页面**：`/rent-dashboard`、`/tenants/:id`、`/cash-receipts/new`、催缴抽屉。四者的表格滚动、面板可关闭、表单可填、无文字重叠均已逐一验证。
- **幂等请求号未被截断**（专门验证过）：实测文本宽 298px，输入框内容区 303px，截图里看起来贴边是错觉。
- **汇总卡片在 ≤640px 已降为单列**，金额 26px 无换行无裁切；筛选栏单列堆叠无重叠。
