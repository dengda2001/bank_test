# Figma 原型还原实施计划

## 任务树与硬依赖

```text
09-18-figma-prototype-alignment（父：产品基线、集成验收）
├─ 09-19-figma-domain-operations      领域写入与数据不变量
├─ 09-19-figma-page-data-routes       页面读取模型、规范路由与动作流程
├─ 09-19-figma-desktop-workspace      桌面端视觉与交互
└─ 09-19-figma-mobile-workspace       移动端视觉与交互
```

硬顺序为：`领域写入 → 页面数据／路由 → 桌面端 → 移动端 → 父任务集成验收`。这不是把实现切成孤立技术层：第一个任务先保证账务和关系写入正确，第二个任务提供同一份受限读取语义，后两个任务只做不同设备的信息表达，因此不会在同一服务端模板和 CSS 上并行互相覆盖。

## 实施前门禁

- 本文仅为执行计划；在用户审阅并明确批准后，才运行 `task.py start` 或修改业务代码。
- 开始前执行 `trellis-before-dev`，读取 `cmd/truelayer-demo` 与涉及的模板／静态资源层规范，并重新检查工作树。当前工作树含其他活动任务的改动，绝不清理、回退或覆盖。
- `09-16-mobile-friendly-workspace` 及其子任务仍在进行。实施时先检查其最终产物；本任务复用其可用的卡片／浏览器验收基础，而不是在同一模板和 CSS 上并行做冲突性改写。

## 分阶段交付

| 阶段 | 交付和验收边界 | 前置依赖 |
| --- | --- | --- |
| 1. 领域安全网 | 可追加的数据库迁移；发票 URL、人工平账原因、有效期安排的服务合同及单元／MySQL 测试 | 无 |
| 2. 资产与入住闭环 | 房产／房间 CRUD 与安全停用；租客创建／编辑时的唯一房间绑定、自动均分、手动改分、未来生效安排 | 阶段 1 |
| 3. 读取模型和新路由 | 总览、账单、流水、催收、资产、租住安排、现金、支出、银行的受限 view model 和规范路由 | 阶段 2 |
| 4. 桌面壳层与页面 | Figma token、深色侧栏、顶栏、表格、详情抽屉和全部桌面页 | 阶段 3 |
| 5. 移动壳层与交互 | 五项底部导航、卡片、详情页、sheet 与 360–430px 适配 | 阶段 4；吸收现有移动任务产物 |
| 6. 集成验证与视觉回归 | 数据完整性、权限、真实浏览器交互、桌面／手机截图与无障碍复核 | 阶段 1–5 |

阶段按顺序推进。原因是资产／入住写入必须先于聚合页面，所有页面必须使用同一读模型，桌面和手机则在稳定语义上呈现不同信息架构。不会创建互相冲突的平行页面实现。

## 阶段 1：迁移、服务和回归测试

1. 确认现有迁移目录、GORM 自动迁移和测试数据库的升级方式；用只追加的迁移新增：
   - `manual_expenses.invoice_url`（可空字符串）；
   - `payment_transactions.manual_adjustment_reason` 或同等明确、可审计的原因字段；
   - 仅当现有关系模型不足以表达有效期排他性时，新增最小索引／约束，不能重写历史账单。
2. 为 URL 定义长度和 HTTP(S) 校验；展示链接时采用安全属性。没有文件表、对象存储或上传端点。
3. 将人工平账改成“带原因”的服务输入，保持行锁、剩余金额计算、幂等／并发保护及原有撤销轨迹。
4. 编写服务测试：无原因拒绝、部分收款后只平剩余、并发不超收、原因在交易／分配历史可见、跨用户 ID 不可访问。

## 阶段 2：资产与自动租住安排

1. 完成房产和房间的用户隔离读写处理器／服务：创建、编辑、详情、停用。房间创建或编辑必须选择属于当前用户的房产。
2. 用内部 `tenancyAgreement`／`agreementParty` 作为版本化的房间月租、账单日和成员责任计划；不增加一套需房东维护的租约表单。
3. 实现单一事务的“未来有效安排”服务：
   - 读取当前房间与现有成员；
   - 按总月租和成员数预填均分；允许提交逐项金额；
   - 验证正数、责任唯一、总额守恒、房间／房产状态、租客单房间规则和未来生效月份；
   - 截止替换的安排并创建不重叠的新安排和全部成员；
   - 空房间不生成月度应收。
4. 改造新租客表单：未选房间时仅创建资料；选房时调用上述服务。旧文本字段不迁移也不推断。
5. 测试：单人、同住均分、同住手调、金额不守恒、同月重复房间、换房、空房、停用阻断、历史账单未变、用户隔离。

## 阶段 3：规范路由和可复用读取模型

1. 建立共享页面 shell、导航状态与响应式 view model，避免每个 Go 字符串模板各自重新计算金额／状态。
2. 添加 `/bills`、`/transactions`、`/dunning`、`/properties`、`/tenancies`、`/bank` 等规范 GET 路由；保留 `/billing`、银行 OAuth／刷新和现金子路由的兼容性。
3. 从现有服务组合以下读取模型，而不是复制账务规则：
   - 月度房产／房间／个人责任聚合与四项指标；
   - 账单余额与每笔来源；
   - 流水匹配状态、建议与处理审计；
   - 催收可发送性及投递历史；
   - 房产／房间／租客／安排详情；
   - 全局现金记录、可关联支出和单授权银行状态。
4. 所有 entity detail、筛选、分页和 postback 都在服务端按当前用户重新查证 ID；保留 URL 筛选状态。

## 阶段 4：桌面 Figma 还原

1. 从两份原型抽出共享 token 和组件：导航、标题区、指标卡、状态、表格、筛选、按钮、抽屉、确认对话框、空／错状态。
2. 建立深色侧栏和 64px 顶栏，按规范路由设置活动项。完成总览、账单、流水、催收、房产、房间、租客、租住安排、现金、支出、银行十一个页面。
3. 使用真实详情数据替代原型中的示例数值；房产、房间、租客和流水详情在抽屉／面板中可导航回对应实体。
4. 强动作验收：人工平账为“原因 → 确认”，催收为“候选 → 预览 → 发送确认”，现金作废和流水撤销均显示影响与必填原因。

## 阶段 5：移动 Figma 还原

1. 在手机断点切换为移动原型的信息架构，不只是压缩桌面布局：顶部栏、首页／账单／流水／对象／更多的固定底部导航。
2. 总览使用两列指标和可展开层级；账单、流水、租客、费用和现金使用纵向卡片。长字段在详情或展开区呈现，不能靠横向大表完成任务。
3. 编辑、平账、催收确认、现金和支出采用底部 sheet；操作命中区至少 44px，主确认按钮固定在安全区上方。
4. 在 360×800、390×844、430×932、600×960 检查无全页水平滚动、无安全区遮挡、可返回和焦点行为正确。

## 阶段 6：验收与交付

1. 运行受影响 Go 单测、MySQL 集成测试及完整测试套件；必要时创建受控测试用户与房产／房间／租客 fixture，测试结束后清理自己的 fixture。
2. 执行真实浏览器流程：
   - 新建房产→房间→未绑定／绑定租客→未来月责任；
   - 银行 refresh-token 同步→流水匹配／撤销；
   - 部分收款→有原因人工平账；
   - 催收预览→强确认→同日重发保护；
   - 房产／房间停用阻断；
   - 支出关联及外部发票 URL。
3. 比对桌面 1366×768、1440×900 和手机 360×800、390×844、430×932 截图与原型，修复层级、间距、状态、溢出和点击可达性偏差。
4. 在提交前运行 `trellis-check`；记录未实现的二期能力（按天分摊等），不以静态原型按钮冒充已上线功能。

## 预期验证命令

实际命令会在开发前按项目规范复核；最低验证集合预计为：

```sh
go test ./cmd/truelayer-demo/...
go test ./...
```

再配合真实浏览器的桌面／手机交互测试与截图检查。包含 MySQL 的测试只在现有受控测试配置可用时运行，绝不对用户数据执行清理。

## 回退点

- 数据库：只追加列、索引和记录；不删除或批量更新历史。
- 路由：旧入口保留，出现 UI 问题可暂时导回兼容页。
- 账务：人工平账、现金、流水、催收全部保持可追溯的撤销／投递记录，不能靠直接 UPDATE 金额“回退”。
