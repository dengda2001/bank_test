# Figma 原型还原评估

## Goal

基于 `figma/rentops-desktop-suite.html`，按页面对照 RentOps 当前可运行的产品能力与原型表达，形成经用户确认的“最大化还原”范围、缺口分级和后续实施路径。在本任务的规划阶段不修改业务代码或视觉实现。

本任务作为父任务保留已确认的产品范围、跨端视觉基线、子任务依赖和最终集成验收；实际代码只在下列子任务中实施。

## Delivery Topology

| 子任务 | 独立交付 | 启动前置 |
| --- | --- | --- |
| `09-19-figma-domain-operations` | 资产／自动租住安排、人工平账原因、发票 URL 以及不变量测试 | 无 |
| `09-19-figma-page-data-routes` | 规范路由、用户隔离的页面读取模型、强确认服务流程接入和共享导航语义 | 领域任务完成 |
| `09-19-figma-desktop-workspace` | 十一页桌面端 Figma 还原与详情抽屉 | 页面数据／路由任务完成 |
| `09-19-figma-mobile-workspace` | 移动端底部导航、卡片、详情和 sheet | 桌面任务的模板契约稳定；并完成与现有移动任务的衔接检查 |

父任务最后执行跨任务集成验收。父子关系不表达依赖，以上顺序同样写入每个子任务自身的 PRD 与执行计划。

## Confirmed Facts

- 原型是一个单文件、可交互的桌面收租运营工作台；左侧导航包含收租总览、应收账单、流水匹配、催收任务、房产、房间、租客、租约、现金补录、费用支出和银行设置，以及房产／房间／租客／流水详情状态。
- 原型约定深色固定侧栏、64px 顶栏、浅色卡片／表格工作区、EUR 金额格式、房产→房间→租客层级和右侧详情抽屉；导出的响应式断点在 760px 将导航与内容改为单列。
- `mobile/rentops-mobile-suite.html` 是独立的移动端原型，而非桌面原型的缩放版：它使用固定顶栏与五项底部导航（首页、账单、流水、对象、更多）、两列月度指标、纵向责任卡片、可展开的房产→房间→租客层级、详情页和底部操作表单（sheet）。
- 移动端原型将租约、催收、现金、支出和银行设置放入“更多”；它定义了 44px 控件、底部安全区、360px 窄屏单列降级与 600px 居中窄工作台。桌面与移动文件共用同一套 OKLCH 色彩、字体、间距、状态与账务术语。
- 用户确认总览的四张首屏指标应遵循原型：本月应收、已收租金、剩余未收、房产支出；当前系统的经营净额不删除，改在房产详情和次级财务信息中呈现。
- 用户确认“应收账单”的“一键平账”语义为人工调整：点击后仅在桌面抽屉／移动 sheet 中填写必填调整原因并二次确认；确认后创建可追溯的人工调整与账单分配。不得要求用户在银行匹配、现金补录、人工调整之间选择；当前无原因的手动平账接口需补充原因字段与审计展示。
- 用户确认“流水处理”沿用真实银行同步机制：桌面与移动端的主按钮都命名为“同步银行流水”，通过当前用户已存银行连接的 refresh token 刷新数据；不将桌面原型的“导入银行文件”实现为日常入口。旧版 JSON／JSONL 迁移能力保留在非日常管理路径。
- 用户确认“催收任务”属于高风险外发动作：桌面端从多选候选项进入邮件内容预览，再显式确认批量发送；移动端在 sheet 内展示收件人、欠款和邮件内容后确认。当天已成功发送的记录必须单独确认才可重发；无有效邮箱或 SMTP／发件配置不完整时必须阻止发送并说明原因。
- 用户确认将资产维护纳入本次范围：房产与房间均应支持新建、编辑和停用，不提供物理删除；房间新建／编辑表单必须从用户自己的房产中选择并绑定一个 `property_id`。历史账务不可改写，后续租金、入住人与责任金额改动只从指定未来月份生效。
- 用户确认保留当前 `tenancyAgreement`／`agreementParty` 数据结构，但不要求房东单独创建或维护租约。租客新增／编辑是唯一的入住配置入口：用户为租客选择房间、设置本次入住的起止日期与个人责任金额，系统自动创建或更新对应的租住安排；“租约管理”页改为自动生成的租住安排读取／历史视图，不作为第二套必填设置。
- 用户确认允许先创建未绑定房间的租客；该记录只保存身份、联系方式与付款人资料，在被分配到房间前不得自动生成租住安排、月度应收或催收候选。
- 用户确认费用发票本轮不实现文件上传、下载或文件存储。支出记录只增加可选发票 URL 字段，支持填写、查看和替换外部链接；原型中的上传控件应替换为链接输入，不能伪装为已上传文件。
- 用户确认银行连接沿用单授权模型：每个系统账号只能绑定一个银行授权（一个 refresh token），该授权下返回的多个实际账户可一并同步；不支持并行维护多个独立银行授权。“新增银行账户”在原型还原中改为“连接银行／重新授权”。
- 用户确认房间维护固定月租与缴租日。租客入住／责任调整从指定未来账单月生效时，系统按该房间当期在住人数自动计算默认均分；房东可逐项手动改写分摊额，但确认前必须校验所有责任金额精确等于房间月租，不能产生未分配或超额应收。
- 用户确认本次不迁移或自动推断历史租客的文本房间资料。既有租客、旧账单与流水保持原样；只有新建租客时才选择真实房间并创建结构化租住安排。新工作台不承诺把旧文本地址归并到房产／房间层级。
- 用户确认本期仅按整月计费：入住／退租日期保留在租客档案与自动生成的租住安排中，用于合同和历史展示；所有租金及责任变更从所选未来账单月的第一天生效，不做首末月按天分摊。按天分摊（日租金、首末月金额、跨月分配）明确留到二期。
- 用户确认停用保护：房产或房间只要仍存在当前或未来的租住安排，就不得直接停用；房东必须先从租客侧完成退租或换房。停用不改写历史账单、收款或流水。
- 用户确认一个租客在同一个账单月只能未绑定或绑定一个房间；换房通过未来月份结束旧安排、开始新安排完成。多人同住仍由多个租客绑定同一房间表达；本期不支持一个租客同时承担多个房间的租住安排。
- 当前可访问路由包括 `/rent-dashboard`、`/billing`（匹配、拆分、忽略、恢复、撤销与付款人确认）、`/tenants`、`/tenants/:id`、`/cash-receipts/*`、`/expenses`、登录／退出。共享导航目前只有月度总览、银行流水、租客管理、支出记录。
- 当前领域层已经具备房产、房间、租约、多人责任、月度应收、收款分配与房间／房产聚合的仓储和服务边界；但这些能力尚未全部成为可访问的管理页面。租客、现金、支出和银行流水已有真实读写流程。
- 已完成的收租工作台明确保留：收款按账单责任月份归集、银行到款与现金补录可追溯、租客可有多个付款人、流水可拆分／续配／撤销、催缴有记录与投递服务；已规划的多房源任务进一步定义房产→房间→租客的月度聚合、同住人与代付。
- 当前工作区另有用户未提交改动；本任务只新增自己的规划材料，不改写或清理既有改动。

## Requirements

- 按原型的每个页面／详情状态列出：用户目标、原型可见功能、当前是否已有真实能力、差距的性质（仅 UI、已有领域能力但缺少页面、需要新增后端／数据模型、原型示意）及可还原程度。
- 反向盘点当前系统已有但原型未表达的功能和约束，明确哪些必须在还原时保留、以何种界面位置或渐进披露方式保留。
- 将原型交互拆分为可直接映射的真实流程与不可承诺为真实功能的演示性控件，避免用静态样例替代账务事实、权限、审计或错误状态。
- 与用户按页面确认信息架构和实施优先级；在用户确认前不启动 UI 或后端实现。
- 视觉评估覆盖全局壳层、桌面／移动响应式策略、可访问性和现有服务端模板架构的适配限制。
- 桌面和移动端分别以 `figma/rentops-desktop-suite.html` 与 `mobile/rentops-mobile-suite.html` 为视觉和交互基线；不能以桌面表格缩放替代移动端原型的底部导航、卡片、详情和 sheet。

## Confirmed Page Scope

| 原型页面 | 本期结论 | 真实功能映射与缺口 |
| --- | --- | --- |
| 收租总览 | 完整还原 | 基于房产→房间→租客的月度聚合；四项指标为应收、已收、未收、房产支出。人工平账补上必填原因与二次确认。 |
| 应收账单 | 完整还原 | 复用 `rent_obligations`、收款分配与现金收据；需把现有直接平账改为带原因的确认流。 |
| 流水匹配 | 完整还原 | 复用银行流水、建议匹配、拆分、撤销、付款人确认；日常入口为 refresh-token 同步。 |
| 催收任务 | 完整还原 | 复用候选、预览、SMTP 投递和审计；补独立页及强确认步骤。 |
| 房产 | 需补管理页 | 新建、编辑、停用、详情和房间聚合；已有领域模型。 |
| 房间 | 需补管理页与有效期写入 | 新建、编辑、停用、房产绑定、逻辑月租／账单日、在住人及责任分摊。 |
| 租客 | 重构现有页 | 身份、联系方式、付款人资料以及唯一当前房间的入住配置；可先创建未绑定租客。 |
| 租住安排（原型“租约”） | 新增只读页 | 由租客／房间操作自动生成，展示当前与历史，不设置独立创建入口。 |
| 现金补录 | 需补全局列表页 | 复用现有预览、入账和有原因作废流程；新增全局查看与原型卡片入口。 |
| 费用支出 | 重构现有页并补字段 | 房产必选、房间可选；增加可选外部发票 URL，不做文件存储。 |
| 银行设置 | 需补独立页 | 一用户一银行授权，展示连接、同步状态和实际同步账户；“新增银行”改为连接／重新授权。 |

所有桌面详情抽屉与移动详情页（房产、房间、租客、流水）属于相应实体页面的验收范围，必须使用真实记录与真实账务聚合，不能保留原型样例数据。

## Existing Capabilities To Preserve

- 付款分配可拆分、续配、撤销；银行原始流水不可被匹配操作改写。
- 现金补录的预览、幂等性和有原因作废；不把现金伪装成银行流水。
- 付款人别名及确认流程、同住人代付和按个人责任催收。
- 催收投递记录、同日重发保护、发送失败／配置缺失的阻断反馈。
- 用户数据隔离、EUR 金额校验、账单归属月份、筛选／分页 URL 与银行同步覆盖状态。

## Explicitly Deferred

- 旧文本房间资料的迁移、自动归并或历史修复。
- 多银行授权、多租客自助门户、团队权限与多币种换汇。
- 发票文件上传、下载、OCR、文件历史和内部文件托管。
- 月中按天分摊、日租金、首末月比例账单与跨月按天结算。
- 同一租客同月多房间，以及独立人工维护“租约”的第二套配置流程。

## Acceptance Criteria

- [ ] 提供原型页面清单，且每个页面均有“可直接复用／需补页面／需补领域能力／原型示意”的明确结论。
- [ ] 提供当前系统独有能力和不可丢失业务约束的清单。
- [ ] 用户已逐项确认目标导航、核心页面范围和保留／后置项的产品边界。
- [ ] 如用户决定实施，`design.md` 与 `implement.md` 定义视觉 token、路由映射、数据流、风险与按页验收方式后，才申请启动实施。
- [ ] 桌面端在 1366px 及以上还原深色侧栏、64px 顶栏、表格／详情抽屉信息层级；手机端在 360px、390px 和 430px 使用独立底部导航、卡片、详情页和 sheet，不依赖宽表横向滚动完成主流程。
- [ ] 新房产、房间及新租客可完成“房产→房间→入住配置→未来月份应收”闭环；分摊默认均分、允许编辑、保存时精确守恒；不触碰旧文本资料。
- [ ] 每个破坏账务或外发的操作均含对应的确认／原因／审计要求：人工平账、现金作废、流水撤销与催收发送。

## Initial Out of Scope

- 本规划任务不直接修改现有页面、数据库、路由或业务规则。
- 不因原型中的示例数据而改变既有 EUR、用户隔离、账务可追溯、月份归属或收款分配约束。
