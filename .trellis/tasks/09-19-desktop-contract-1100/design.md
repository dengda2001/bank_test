# 技术设计：桌面契约解冻与 1100 断点

父任务 `design.md` 的架构与边界同样适用，此处只记录本子任务独有的决策。

## 1. 边界

改：`.trellis/spec/frontend/responsive-conventions.md`、`web/static/css/workspace.css`、受影响的 `web/static/css/pages/*.css`、`mobile_layout_test.go` 及相关断言。

不改：任何页面 HTML 结构、Go 视图模型、路由契约。

## 2. 关键决策

### 2.1 1100 档放在共享表里可能不够 —— 需要实机验证

`responsive-conventions.md:83` 记录了一个决定性事实：`html/template` 把共享样式表拼在页面样式**之前**，因此**共享表在同等优先级下必输**给页面局部规则。

新增的 1100 档若只写在共享表里，且选择器与页面局部规则同优先级，那么页面局部规则仍然胜出，1100 档形同虚设。这是本子任务最容易做错的地方 —— 样式表里"有这条规则"与"这条规则生效"是两回事。

处置顺序：

1. 先按共享表实现 1100 档。
2. **实机测量** 1024 档下是否真的生效（不读 CSS，看渲染几何）。
3. 若不生效，改用更高选择器优先级；仍不够则退回"共享表放令牌与基线 + 各页面表各自追加 1100 档"。

步骤 2 是硬性要求。这个节点不做实机验证，后面四个子任务都会建立在错误基线上。

### 2.2 980 / 981 这一对的处置

现有 `max-width:980px` 与 `min-width:981px` 是一对互补规则。处置前必须先查清它们各自承担什么：

- 若只是历史遗留的桌面/窄屏切换，且被 640 档完全覆盖 → 删除。
- 若承担了 640–980 区间的行为 → 并入 1100 档，并记录合并后的区间语义。
- 若承担了跨页面的独立行为 → 保留，并在 spec 中补上它此前未被记录的理由。

**先查清再决定**，不要因为"看起来重复"就删。删除前先确认没有测试或页面依赖它。

### 2.3 冻结契约改成什么

不能简单删掉 `:17` 那段 —— 那会把约束变成"随便改"。新的表述要满足三个条件：

- 桌面**可以**按原型对齐（否则本次任务无法进行）。
- 任何桌面改动必须**在同一批**更新受影响断言（否则测试会长期失败或被绕过）。
- 每处桌面改动要能说清改的是哪一处原型差异（否则无从复核）。

## 3. 兼容与回滚

- 640 档的规则与断言是本次的**不变量**。改动前后用 diff 证明它们未变。
- 本子任务是纯基线改动，不含视觉成果，可独立 revert。

## 4. 验收方式

- 四档（1024 / 1366 / 1440 / 1920）实机渲染，断言 `scrollWidth === clientWidth`。
- 截图存入 `research/screenshots/`，作为 ②③④⑤ 的对照基线。
- 复用 `scripts/audit/` 的 `desktop-full.mjs`（桌面回归对）与 `probe-wide.mjs`（区分页面级溢出与滚动容器内溢出）。被测实例由 `scripts/run-audit-local.sh` 起，不指向 `:8081` / `bank.ddpl.top`。
