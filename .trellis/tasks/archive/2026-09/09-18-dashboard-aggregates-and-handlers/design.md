# 设计：聚合查询与后端接口

## 1. 目标与边界

本任务把已生成的 `rent_charge` / `rent_obligations`、有效付款覆盖和房产/房间主数据聚合成月度工作台数据，并通过现有 Go HTTP 页面提供三个视角和房间详情。模板仍暂时留在 Go 字符串中；模板外置、桌面/移动 CSS 边界放到后续子任务。

本任务负责：

- 房产、房间、租客三个视角的统一月份查询、筛选、排序和分页。
- 房间空置与“有租约但缺账单”的待处理区分。
- 房产级房间数量、收缴指标、支出和经营净额聚合。
- 房间详情页的租约账务、租客责任、付款来源和明确归属支出。
- 保留现有付款确认、分配、撤销、现金补录和催缴 handler 的入口，并让新工作台链接携带上下文。

不负责房产/房间初始化、跨房间付款入口、模板文件外置或移动端重构。

## 2. 页面接口契约

### 月度工作台

`GET /rent-dashboard`

查询参数：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `period` | 当前月份 | `YYYY-MM`，服务端统一归一到月份首日 |
| `view` | `properties` | `properties`、`rooms`、`tenants` |
| `property_id` | 空 | 用户范围内的房产筛选；房间视角下保留为下钻上下文 |
| `room_id` | 空 | 用户范围内的房间筛选 |
| `search` | 空 | 名称、别名、房产名、房间号/地址匹配 |
| `status` | `all` | `all`、`unpaid`、`needs_review`、`overdue`、`partial`、`open`、`paid`、`vacant` |
| `sort` | `status` | 默认严重度排序，其他排序由视角数据决定 |
| `page` / `page_size` | `1` / `12` | 最大每页 50 |

响应保持 HTML 页面，不暴露数据库模型。页面数据包含统一顶部金额摘要和当前视角行集合：

- `properties`：每个房产一行，包含有效房间总数、已交满/未交满房间数、应收、已收、未收、收缴率、当月支出和经营净额。
- `rooms`：每个有效房间一行；空置房金额和到期日为 `—`，可进入 `/rooms/{room_id}?period=YYYY-MM`。
- `tenants`：每个“租客 × 房间 × 月份”责任一行，包含责任、覆盖、未付、状态及付款来源；代付不改变实际付款人投影。

所有 `property_id` / `room_id` 先以 `user_id` 查询目标，不存在或越权统一按未找到处理，不能用文本字段回退。

### 房间详情

`GET /rooms/{room_id}?period=YYYY-MM`

只接受正整数路径 ID 和合法月份。返回房间主数据、所选月份 charge/obligations、有效收款明细、明确 `room_id` 的有效支出及当前上下文返回链接。没有目标、跨用户目标和路径格式错误返回明确 404/400 页面，不自动选择其他房间。

现有写操作继续使用：

- `/billing/confirm`、`/billing/allocate`、`/billing/revoke`：付款预览后的确认、拆分和撤销。
- `/cash-receipts/new`、`/cash-receipts/void`：现金补录和撤销。
- `/dunning/preview`、`/dunning/send`：租客责任催缴。
- `/expenses`：支出维护；房间详情只读取明确归属该房间的支出。

## 3. 聚合口径

查询服务一次读取用户范围内的有效 properties、rooms、period charges、obligations、付款分配、现金收款和支出，再在 Go 中按稳定 ID 聚合；任何金额字段都不从页面缓存列推导新的业务事实。

- 房间总应收/已收/未收只来自该月 active charge 下的 active obligations；余额为 `max(expected - paid, 0)`。
- 有 active agreement 且有 active party，但 charge 缺失：`needs_review`；没有该月有效租约/参与人：`vacant`。
- 房产总房间数包括该月有效的所有可出租房；空置房不进入金额、已交满或未交满计数。
- 房产支出包含有效的 `property_id = property` 支出及其下明确 `room_id` 的支出；房间详情只包含明确 `room_id` 的支出。
- 其他收入只有在来源事实带有稳定房产归属时才能进入房产经营净额；当前既有未归属收入仍保留在全局待处理/未分配口径，不猜测所属房产。

状态排序统一为：`needs_review -> overdue -> partial -> open -> paid -> vacant`。房产取其房间最严重状态；同状态按未收金额降序，再按名称/ID 稳定排序。筛选和分页只作用于行，不改变顶部汇总。

## 4. 错误语义与兼容

- 未认证继续由现有 `requireAuth` 处理。
- 查询参数无效返回 200 的页面级错误提示并使用安全默认值，保持当前服务器渲染行为。
- 目标资源不存在、越权或 URL 路径不合法返回明确 404/400，不返回另一用户或任意第一条记录。
- 旧数据仍走兼容的租客月账单路径；新房产视角只使用有明确 charge 归属的数据。
- 新工作台查询服务不直接暴露 GORM model，下一任务可将页面数据结构搬到独立模板/API 适配层。

## 5. 风险

- 旧租客数据与新房间数据可能同时存在，必须避免同一月份在工作台重复计入；新视角只聚合 `rent_charge_id` 非空的账务事实。
- 当前其他收入表结构没有稳定 `property_id`，因此不能按文本提示归属房产；实现选择显示为未归属，而不是猜测或分摊。
- MySQL 查询和并发生成由前置任务负责；本任务增加真实多房产查询测试，并在没有 DSN 时按项目约定跳过。
