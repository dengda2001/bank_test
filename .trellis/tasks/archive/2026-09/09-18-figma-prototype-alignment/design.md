# Figma 原型还原技术设计

## 1. 实现边界

本次是在现有 Go 服务端渲染应用上重构，不引入 SPA、前端 API 层或另一套账务计算。处理器继续从同一 MySQL 领域模型读取数据，模板只负责按桌面／手机断点呈现；任何金额、状态、可执行动作都必须来自既有服务或新增的领域服务，不能把 `figma/` 或 `mobile/` 的样例数据带入运行时。

桌面以 `figma/rentops-desktop-suite.html` 的固定深色侧栏、64px 顶栏、浅色工作区、表格与右侧详情为基线。手机以 `mobile/rentops-mobile-suite.html` 的五项底部导航、两列汇总、纵向卡片、独立详情页和底部 sheet 为基线；手机主流程不得依赖桌面宽表格的横向滚动。

## 2. 信息架构与路由

| 产品页 | 规范路由 | 保留／兼容路由 | 主要真实数据 |
| --- | --- | --- | --- |

## 3. 领域模型与写入规则

### 3.1 房产、房间与逻辑月租

- `property` 和 `room` 继续是唯一的资产实体。房间始终通过 `property_id` 绑定属于当前用户的房产。
- 房间表单显示“月度房间应收”和“账单日”。为避免改写历史，这两个用户可见的当前值由该房间最新有效的 `tenancyAgreement` 承载；该记录是内部自动生成的价格／责任版本，不要求房东单独管理“租约”。
- 创建空房间时建立其首个内部月租计划，但没有租客责任时不得生成应收。后续首次入住或任何未来生效的租金／成员变更均关闭旧有效计划（结束日为生效月前一天），新建一个不重叠的计划。
- 房产／房间编辑不得改写已经生成的 `rent_charges` 或 `rent_obligations` 快照。停用仅在没有当前或未来有效安排时可提交。

### 3.2 租客作为唯一入住配置入口

租客表单分为“资料与付款识别”和可选的“入住安排”区：

1. 未选择房间：只写身份、联系方式、付款人信息和可选合同日期；不写月租责任，不产生应收或催收候选。
2. 选择房间：选择入住生效月份（仅未来月份）、合同入住／退租日期和该房间的全体在住人分摊。系统读取该房间的有效总月租和账单日，默认按人数均分（余数按最小货币单位确定分给固定排序的成员），房东可改每个金额。
3. 保存前验证：所有责任金额为正、同房责任人唯一、金额总和严格等于房间月租；租客在同一账单月只能出现在零个或一个房间；房间和房产都必须仍有效。
4. 保存时在同一数据库事务内写入新的自动 `tenancyAgreement`、全部 `agreementParty`，并收束被替换安排的结束日。失败时不留下半份成员配置或部分应收。

`agreementParty.JoinedAt`／`LeftAt` 和自动安排的开始／结束日保存合同时间；一期账务一律从生效月首日变更并生成整月责任。日租、月中比例和首末月拆分属于二期，当前表单须明确提示此限制。

既有租客的 `RoomLabel`、`RoomAddress`、`PropertyHint`、个人月租和旧账务保持兼容读写，但不被自动映射到新关系模型。新工作台的资产层级只显示真实绑定的新增安排。

### 3.3 审计型写入

- **人工平账**：由账单详情／列表打开桌面抽屉或手机 sheet，显示未收金额，要求填写原因，再显式确认。服务在行锁保护下创建恰好等于最新未收余额的 `manual_balance` 收入交易及分配，并把原因作为单独的审计字段保存／展示；双击或并发请求不得超额入账。
- **现金**：继续使用现有预览、幂等键、金额锁定和有原因作废；全局列表只是新的读取面，不绕过原流程。
- **流水**：银行原始交易、拆分、确认、忽略、恢复与撤销继续通过现有交易服务。新页面只改变入口和层级，绝不修改原始银行描述或金额。
- **催收**：候选选择后进入预览，显示收件人、欠款、邮件正文和不可发送原因；再次确认才调用投递。当天已成功投递的项目默认不可选，用户必须逐项明确确认重发。

### 3.4 支出和发票链接

`manual_expenses` 增加可空 `invoice_url`。新支出以真实房产为主关联，可选再关联该房产下的房间；写入时验证归属关系和用户隔离。发票区域是一个可替换的 HTTP(S) 外部链接输入与安全的新窗口查看链接，不上传、不代理、不下载、不保存文件内容或版本历史。旧未关联支出继续可读，作为“未归属”记录，不主动迁移。

### 3.5 银行授权

`bank_connections` 按用户、provider、environment 保持一个当前 refresh token。连接或重新授权会安全替换该 token；刷新会使用它获得 access token、处理 token 轮换、同步授权下返回的所有实际账户，并记录同步运行、覆盖范围和成功／失败状态。银行页不得提供多个独立授权的“新增账户”语义。

## 5. 视觉与可访问性契约

- 抽取原型 OKLCH token（背景、表面、深色导航、绿色主动作、告警和危险状态）、系统字体、tabular 数字、边框与半径作为共享 CSS 变量；不能继续逐页复制蓝色旧样式。
- 桌面保持信息密度与键盘可达的表格。详情抽屉打开后设置焦点、可用 Escape 关闭、不会把背景操作留在焦点顺序中。
- 手机在 360／390／430px 以单列卡片和最小 44px 命中区运行；600px 以内是居中的窄工作台，安全区和固定底部导航不覆盖主按钮。表单、强确认和撤销在 sheet 内使用粘性确认栏。
- 状态不能只用颜色表达；金额使用 EUR 与等宽数字。错误、无数据、同步不完整、无邮箱和不可发送原因必须有文字说明。

## 6. 兼容性、风险与回退

- 先新增字段和写入服务，再切换页面；保持 `/billing`、银行 OAuth、现金和催收旧 POST 路由可用，避免深链失效。
- 用户数据隔离在每一个新读取、实体选择、详情和写入点重新校验，绝不只信任表单 ID。
- 未来生效的安排必须防重叠、验证责任守恒并采用事务；历史应收一旦发出，只能通过现有收款、人工平账或撤销审计改变余额。
- 前端部署异常可将新入口暂时重定向回旧兼容路由；数据库字段只做可回滚的追加，不删除旧列或历史记录。
