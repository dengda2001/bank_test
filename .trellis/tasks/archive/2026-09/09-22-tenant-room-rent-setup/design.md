# 设计：新增租客联动入住与房间租金

## 1. 设计结论

继续以 `room_rent_plans` / `room_rent_plan_members` 为租金与分担的唯一事实源，不把租金字段重新加回 `rooms` 或 `tenants`。本次只增加两个面向房东的组合写入入口：

```text
新增房间
  → 房间资料 + 空成员租金计划（同一事务）
  → 可选跳转“新增租客”，预选房产、房间和生效月

新增租客（可不选房间）
  → 租客资料 + 付款识别
  → 若选择房间：读取目标月份计划和已有成员
  → 保存包含新租客在内的完整下一版计划（同一事务）
```

“备注”仅是租金输入旁的静态表单提示，不增加数据库列。

## 2. 页面交互

### 2.1 新建房间抽屉

- 保留房间名称、所属房产和房间备注。
- 增加必填“房间月租（EUR）”、必填“租金生效月份”和必填“每月交租日”。
- 生效月份使用 `type="month"`，默认都柏林当前月；交租日默认 1，范围 1–31。
- 两个提交动作都会原子创建房间及空成员租金计划：
  - “仅保存空房间”返回原房间／房产页面。
  - “保存并设置租客”跳到 `/tenants?add=1`，并通过查询参数预选刚创建的房产、房间和租金生效月份。

### 2.2 新增租客抽屉

- 编辑现有租客时继续只编辑人员资料和付款识别；本次不把换房、退租或历史计划调整塞入资料编辑。
- 新增状态增加“入住与租金（可选）”区块：房产、房间、入住生效月份、新租客租金。
- 房产选择后，房间下拉只显示该房产下且在目标月份存在租金计划的有效房间。
- 房间与月份确定后显示房间总租金、交租日和目标月份已有租客。
- 新租客单独放在主编辑区；已有租客放在独立弱化区，姓名和当前分担只读，仅“调整后租金”可输入。
- 所有租金输入默认留空，旁边显示“留空则按照入住人数均分房间租金”。页面实时预览固定金额、待均分人数、剩余金额和最终合计。
- 未选择房间时仍可只保存租客档案。

## 3. 页面数据合同

服务端向新增租客抽屉提供当前用户作用域内的房产与房间计划选项。建议使用页面 DTO，不把 GORM 模型直接暴露给模板：

```go
type tenantRoomOption struct {
    ID, PropertyID, TimelineVersion uint64
    PropertyName, RoomLabel         string
    PlansJSON                       string
}

type tenantRoomPlanOption struct {
    EffectiveFromMonth string
    EffectiveToMonth   string
    MonthlyRentCents   int64
    MonthlyRentValue   string
    Currency           string
    DueDay             int
    Occupants          []tenantRoomOccupantOption
}
```

`PlansJSON` 仅用于浏览器切换房产、房间和月份后的预览。提交时后端重新查询房间、计划、成员、租金、交租日和时间线版本；不信任浏览器提交的显示金额或成员名单。

表单提交包含：`property_id`、`room_id`、`arrangement_start_month`、`plan_version`，以及完整成员调整 JSON。新租客使用占位 ID `0`，在事务内创建租客后替换为真实 ID。已有成员集合必须与目标月份当前计划完全一致，否则按陈旧页面拒绝并要求刷新。

## 4. 分担算法

扩展 `validateRoomRentPlanCommand` 的零值语义：`ResponsibilityCents == 0` 表示该成员未指定金额，而不是零租金。

1. 成员为空：允许保存空房租金计划，不生成租金事实。
2. 所有成员金额为零：按排序后的稳定租客 ID 均分全部房租，余数按既有规则分配。
3. 部分成员金额大于零：已填金额固定；房间租金减去固定金额后，按稳定租客 ID 均分给金额为零的成员。
4. 所有成员均填写：总和必须精确等于房间租金。
5. 固定金额总和不小于房间租金且仍有留空成员、任何最终责任不为正、溢出、重复成员或总和不守恒：返回 `ErrInvalidRentPlan`。

前端预览复制相同的用户可见算法，但后端函数是最终权威。

## 5. 原子写入边界

### 5.1 创建房间与租金计划

增加组合命令（名称按实现代码风格落定），在一个 GORM 事务中：

1. 校验房间资料、租金、生效月份和交租日。
2. 锁定并校验所属房产为当前用户所有。
3. 创建房间。
4. 以房间初始时间线版本创建空成员 `room_rent_plan`。
5. 增加 `rooms.rent_plan_version`。

任一步失败都不留下无租金房间。保留底层 `createRoom` 给已有测试／内部调用，但生产新增房间 handler 使用组合命令。

### 5.2 创建租客与更新计划

增加组合命令，在一个事务中：

1. 校验租客资料、可选付款人信息和入住表单结构。
2. 创建租客与付款识别记录。
3. 若未选择房间，提交事务并结束。
4. 锁定房间并比较 `ExpectedTimelineVersion`。
5. 查询目标月份唯一有效计划及完整成员，校验房产、成员集合和当前用户作用域。
6. 把新租客占位 ID 替换为新 ID，运行统一分担算法。
7. 复用租金计划的事务内保存核心：检查资金事实锁、替换时间线、写完整成员、增加版本，并在当前／历史月份按既有规则固化事实。

计划保存失败时，租客与付款识别也一起回滚，避免半成品。

## 6. 空成员计划与月度事实

数据库结构已允许 `room_rent_plans` 没有成员，不需要 migration。需要收敛以下行为：

- `SaveRoomRentPlan` 允许空成员，但只保存租金规则和时间线。
- 空成员计划不调用 `materializeRoomRentFactsInTx`。
- `ensureMonthlyRentFacts` 只把至少有一个成员的计划加入生成目标；`ensureRentCharge` 遇到空成员计划也不创建只有总额、没有个人责任的 charge。
- 房间详情可展示空房租金和交租日，同时明确“暂无入住租客／不会生成个人应收”。

## 7. 错误与兼容

- 继续使用 `ErrInvalidRentPlan`、`ErrStaleRentPlanTimeline`、`ErrRentPlanFactsLocked`、`ErrTenantRoomMonthConflict` 等现有领域错误。
- 新增租客 handler 将计划错误映射成稳定的中文表单提示，并重新打开新增抽屉；跨用户或不存在的房产／房间返回安全的未找到或表单错误。
- 旧房间若目标月份没有租金计划，不可在租客表单中绑定，并提示先设置房间租金。
- `save_and_setup` 的内部 action 值可以保留以兼容既有提交，但用户可见按钮和成功跳转改为“保存并设置租客”。
- 不增加 schema migration，不改写历史 charge、obligation、付款、现金或催收记录。

## 8. 风险与回滚

- 最大账务风险是空成员计划被月度读取错误固化；通过生成目标过滤和 ledger 防御测试双重保护。
- 最大并发风险是抽屉打开后同房成员或租金计划变化；沿用 `rent_plan_version` 乐观锁，并校验提交成员集合。
- 最大交互风险是已有租客与新租客混淆；模板结构、弱化样式和浏览器点击验收共同覆盖。
- 回滚可恢复原抽屉与 handler；新增组合服务不改变表结构，已创建的空成员计划仍是合法时间线数据。

## 9. 规范影响

当前 backend spec 写明房间／租客表单不得写租金计划，这是 migration 014 收口时的旧限制。本次不是恢复 `rooms`/`tenants` 租金字段，而是让表单调用同一个房间租金计划服务。实现完成并验证后，需要更新该规范为“组合表单可以写计划，但不得形成第二事实源”。
