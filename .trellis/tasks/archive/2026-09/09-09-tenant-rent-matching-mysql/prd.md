# 租客租金匹配 MySQL Demo

## 目标

设计并实现 RentOps 下一阶段 demo：把当前本地 JSON/JSONL 状态迁移到
MySQL 兼容存储，让租客管理真正支持收租业务，把银行流水映射到租客租金账单，并让操作者能按月份查看每个租客的交租情况、匹配/未匹配流水和支出。

一期目标是本地 MySQL demo；存储和业务接口边界必须适配后续远程 MySQL，不把本地连接细节写死在 handler 或页面逻辑里。

## 用户价值

- 房东录入租客和租金规则后，不需要每月手工对银行流水。
- 已拉取的银行流水可以匹配到租客应收租金。
- 操作者可以快速看到每个租客本月已付、未付、部分支付、逾期或需要审核。
- 流水表可以区分已匹配租金、未匹配收入和支出流水。

## 已从代码库确认的事实

- 当前应用是 `cmd/truelayer-demo/main.go` 中的单进程 Go HTTP 服务。
- 当前已有 demo 账号密码登录，以及受登录保护的 `/billing`、`/tenants`、`/expenses` 页面。
- 当前已有 TrueLayer OAuth callback 和 refresh token 刷新流程。
- 银行账户、余额、交易 payload 当前追加写入 `TL_LOG_FILE` 指向的 JSONL 文件。
- `/billing` 当前读取最新一条 JSONL 结果并渲染收入交易。
- 当前收入判断逻辑是 `transaction_type == "CREDIT"` 或金额为正。
- 当前收入归一化会尝试从 TrueLayer 原始交易字段和 `meta` 中提取 payer、remitter、counterparty、reference 等字段。
- 当前租客记录是本地 JSON 数组，字段包括 `name`、`monthly_rent`、`currency`、`room_address`、`created_at`。
- 当前支出记录是本地 JSON 数组，字段包括 `description`、`category`、`amount`、`currency`、`expense_date`、`payment_method`、`created_at`。
- README 目前说明租客和支出页面只是本地 JSON 文件存储；本任务会用数据库存储取代这部分。
- `.trellis/spec/backend/database-guidelines.md` 目前记录的是“尚无数据库，使用本地 JSON 文件”的过渡约定。
- 历史 V1 设计文档已经提出统一交易池、应收账单、匹配建议、支付分配、月度账单状态和多维筛选。
- 历史 V1 设计文档明确：产品核心不是银行 API，而是统一交易池和对账/匹配引擎。

## 已确认产品决策

- 一期只实现月租周期。
- 数据模型必须为未来扩展收租周期预留字段：建议使用 `interval_unit`、`interval_count`、`billing_start_date`、`due_day`。
- 一期 UI 可以只暴露“每月收租、每月几号应收、从哪天开始”，但数据库和服务层不要写死成只能表达月租。
- 一期要提供一次性导入能力，把已有银行 JSONL 流水导入 MySQL。
- 现有租客 JSON 和支出 JSON 也可以一起做一次性导入；它们是辅助小功能，不需要做成长期双写或复杂迁移系统。
- 银行流水中已经能看到付款方姓名和 ID；租客资料要支持补充银行付款方 ID。
- 匹配优先使用付款方 ID；租客没有付款方 ID 时，允许按付款方姓名/租客姓名匹配。
- 通过姓名匹配上的记录需要人工确认；确认后可以把流水中的付款方 ID 回填到租客资料，后续同一付款方优先用 ID 自动匹配。
- 月度应收账单采用“懒生成并入库”：打开某个月账单或同步流水需要某个月账单时，如果该月租客应收不存在，就根据租客月租规则生成并保存。
- 一期不需要做批量预生成 UI，但账单生成逻辑必须放在服务层并保留批量生成入口，后续可以一次性生成多个租客/多个月份的应收账单。
- 金额匹配规则：
  - 付款方 ID 匹配成功，且交易落在同一账期内，金额等于应收时自动标记已付。
  - 付款方 ID 匹配成功，且金额小于应收时自动计入部分付款。
  - 付款方 ID 匹配成功，但金额大于应收时进入待审核，不自动全额确认。
  - 只有姓名匹配、但租客还没有付款方 ID 时，生成候选匹配并等待人工确认。
  - 只有金额和日期接近时，不自动匹配，只能作为候选或未匹配收入。
- 账期归属规则：
  - 匹配时先解析银行流水 `description`、`reference`、`meta` 中可能出现的月份信息。
  - 如果备注中的月份能对应到该租客某个月租应收，且该月尚未结清，则优先匹配该月份。
  - 如果备注没有可识别月份，再按付款日期寻找合理范围内的未结清月租应收。
  - 如果备注月份已结清、月份含糊、或同一交易可能对应多个账期，则进入待审核。
- 一期备注月份解析支持：
  - `2026-09`、`2026/09`；
  - `09/2026`；
  - `Sep 2026`、`September 2026`；
  - `Sept rent`、`September rent`；
  - `9月`、`2026年9月`；
  - `rent Sep`、`rent 09`。
- 备注只有月份、没有年份时，根据交易日期附近推断年份，例如 2026 年 10 月 2 日的 `Sept rent` 推断为 2026-09；推断结果仍必须满足该月账单未结清。
- 支出一期先做统一展示和筛选，来源包括银行流水中的 `DEBIT`/负数交易，以及手动录入支出。
- 支出记录预留 `room_hint` 和 `tenant_hint` 文本字段，用来记录房间/租客线索；一期不强制关联真实房间或租客，也不做支出分摊。
- 月度页面可以展示本月总支出，但支出不影响租客交租状态。
- MySQL schema 采用项目内显式 SQL migration 文件管理。
- 应用启动时检测并执行尚未应用的 migration；数据库中使用 `schema_migrations` 表记录版本。
- 本地 MySQL 和后续远程 MySQL 通过同一套 DSN 配置切换，不允许把本地连接细节写死进 handler 或业务逻辑。
- 一期数据库访问使用 GORM 和 MySQL driver。
- 虽然使用 GORM，一期 schema 仍由显式 SQL migration 管理；GORM 负责 CRUD 和查询，不在生产启动路径使用 `AutoMigrate` 自动改表。
- `/billing` 保留，但定位调整为“银行流水页”：只展示流水和流水筛选，去掉月度交租工作台、租客状态等混合内容，并修改为更适合表格查看的样式。
- 新增独立工作台页面 `/rent-dashboard`，侧边栏名称为 Rent Dashboard，用来展示月度交租情况、租客账单状态、匹配进度和月度汇总。
- 一期人工确认采用轻量交互，不做完整审核中心：`/billing` 流水表中，姓名匹配但未确认的交易显示候选匹配和确认按钮。
- 人工确认候选匹配后，系统创建交易到账单的分配记录；如果流水有付款方 ID 且租客还没有付款方 ID，就把该 ID 回填到租客资料。
- 一笔交易如果有多个租客候选，一期不自动显示单按钮确认，先标记为待审核/未确认，避免误操作。
- 租客有效期一期使用 `rent_start_date`、`rent_end_date` 和 `status`。
- `rent_start_date` 必填；`rent_end_date` 可空；`status` 至少支持 `active` 和 `inactive`。
- 生成某个月应收账单时，只给该月和租客有效期有交集的租客生成。
- 一期不做月中入住/退租的按天折算；只要当月有效，就按整月租金生成，后续再扩展 prorate。
- 一期不建正式房源/房间表；租客表先保存结构化房间文本字段：`room_label`、`room_address`、可选 `property_hint`。
- 后续可以把 `property_hint`、`room_label`、`room_address` 平滑升级为正式 `properties`、`rooms`、`tenancies` 模型。
- 必须有账号隔离：不同登录账号只能看到和操作自己的租客、银行流水、支出、月租应收、匹配/分配记录。
- 银行 refresh token 必须跟随账号保存和读取；不能继续作为全局 token 文件共享给所有账号。
- 一期不做账号管理页、注册页、改密码页。
- 一期使用数据库 `users` 表作为真实账号来源；环境变量中的默认管理员账号密码只用于启动时初始化第一条用户记录。
- 如果需要更多账号，可以由操作者直接插入数据库用户记录；应用只负责登录和按 `user_id` 隔离数据。
- 用户密码必须使用 bcrypt 哈希存储，`users` 表不保存明文密码。
- 启动时初始化默认用户时，把 `APP_ADMIN_PASSWORD` 通过 bcrypt 哈希后写入 `users.password_hash`。
- 手动插入额外用户时，也需要插入 bcrypt hash。
- 银行 refresh token 默认加密后保存到 MySQL，并按 `user_id` 隔离。
- token 加密使用 `BANK_TOKEN_ENCRYPTION_KEY` 配置；每个 token 使用随机 nonce。
- live 环境没有 token 加密密钥时必须启动失败；本地 demo 可通过显式 `ALLOW_PLAINTEXT_TOKENS=1` 允许明文 token 作为开发逃生口。

## 需求

- 使用 MySQL 兼容持久化取代 JSON 文件，覆盖租客、支出、银行交易、租金应收、匹配/分配数据。
- 一期必须能连接本地 MySQL。
- 数据库连接配置要能后续切换远程 MySQL，不需要改 handler 和业务逻辑。
- 数据库 schema migration 放在仓库内，例如 `migrations/001_initial_mysql.sql`。
- 应用启动时自动执行未应用 migration；migration 失败时服务启动失败并显示明确错误。
- 使用统一数据库连接配置，例如 `MYSQL_DSN` 或 `DATABASE_URL`，本地/远程 MySQL 只改变配置。
- GORM 只作为数据库访问层，不把 GORM model 直接泄漏到页面模板和匹配业务之外；handler 通过服务层调用。
- GORM model 必须和 SQL migration 对齐；生产启动路径不使用 `AutoMigrate` 改表。
- 租客管理至少支持：
  - 租客姓名；
  - 银行付款方 ID；
  - 银行付款方姓名/别名；
  - 租金金额；
  - 币种；
  - 房间/地址；
  - 收租周期字段；
  - 账单开始日期；
  - 每月应收日期。
  - 收租开始日期；
  - 收租结束日期；
  - 租客状态。
  - 房间编号/标签；
  - 房间地址；
  - 可选物业/房源线索。
- 一期必须建立账号作用域，所有业务表至少带 `user_id`；查询、创建、匹配、导入和刷新都必须按当前登录账号过滤。
- 登录必须查询 `users` 表验证账号密码；session cookie 保存签名后的用户身份，而不是只保存 env 用户名。
- 登录验证使用 bcrypt 校验 `users.password_hash`。
- TrueLayer refresh token 需要迁移到账号维度存储；当前本地 token 文件只能作为旧 demo 兼容或一次性导入来源，不能作为新 MySQL 版本的长期 token source。
- `bank_connections` 表不保存明文 access token；refresh token 存密文，除非本地显式启用明文逃生口。
- 一期只生成或派生月租应收记录。
- 一期的月租应收必须生成成稳定数据库记录，作为流水匹配、人工确认、部分付款和月度状态计算的目标对象。
- 月租应收生成逻辑必须支持按单月懒生成，也要能被后续批量生成任务复用。
- 月租应收生成必须尊重租客有效期；一期不做按天折算。
- 应用必须把银行流水写入数据库中的归一化交易表，而不是只读取最新 JSONL 展示。
- 应用必须提供一次性导入入口或命令，把 `TL_LOG_FILE` 指向的历史 JSONL 银行 payload 归一化写入 MySQL。
- 一次性导入可以同时读取 `RENTOPS_TENANT_FILE` 和 `RENTOPS_EXPENSE_FILE` 指向的旧 JSON 数组并写入 MySQL。
- 银行流水入库必须具备幂等能力：重复刷新或重复读取同一批 provider payload 时，不能产生重复可见交易。
- 匹配层必须把银行收入交易关联到租客的月租应收记录。
- 匹配应优先使用结构化字段，例如 payer/remitter/counterparty ID、payer/remitter/counterparty 名称、reference、金额、币种和付款日期。
- 自动匹配优先级：
  - 租客已保存付款方 ID，且流水付款方 ID 一致；
  - 租客没有付款方 ID，但流水付款方姓名能匹配租客姓名或付款方别名，并且金额/日期合理；
  - 仅金额和日期接近但无法确认身份的交易进入待审核，不自动确认。
- 人工确认姓名匹配或待审核匹配时，系统应支持把该流水的付款方 ID 保存到租客资料，作为后续稳定匹配依据。
- 匹配结果必须支持部分付款：同一个月租应收可以关联一笔或多笔已确认付款，状态由累计已付金额计算。
- 月度交租视图按交易最终分配到的账期统计，不简单按交易发生月份统计。
- `/billing` 候选匹配确认成功后，`/rent-dashboard` 对应账期的已付金额和状态必须更新。
- 如果无法高置信匹配，交易必须留在未匹配/待审核列表，不能静默忽略。
- 新工作台页面必须展示每个租客的应收金额、已匹配支付金额、未付余额、账期、应收日和状态。
- `/billing` 流水表必须支持筛选：
  - 已匹配租金收入；
  - 未匹配收入；
  - 支出/转出；
  - 月份或账期。
- 侧边栏必须包含新工作台入口、流水入口、租客入口和支出入口。
- 支出可以先来自银行 DEBIT/负数交易和手动录入支出，统一展示为支出类记录。
- 手动支出录入支持可选房间线索和租客线索字段。
- 一期不要求支出必须关联租客或房间；后续可把 `room_hint` / `tenant_hint` 平滑升级为正式 `room_id` / `tenant_id`。
- 所有列表和汇总必须基于当前账号作用域；不能跨账号统计。
- 现有登录保护不能退化。
- 现有 token 处理不能退化：refresh token 仍要本地保护；access token 不能随意持久化。
- 原始 provider payload 可以保留用于审计/调试，但 UI 和匹配逻辑必须使用类型化的归一化数据表。

## 验收标准

- [ ] 本地 MySQL 运行时，可以创建、列出租客，并在应用重启后仍保留。
- [ ] 租客记录包含姓名、银行付款方 ID/别名、租金、币种、房间/地址、月租周期字段、账单开始日期和每月应收日期。
- [ ] 租客记录包含收租开始日期、可选收租结束日期和状态。
- [ ] 租客记录包含 `room_label`、`room_address` 和可选 `property_hint`；一期不要求正式房间表。
- [ ] 月度应收不会为有效期外的租客生成。
- [ ] 月中入住或退租一期按整月金额处理，并在 README 或页面文案中说明。
- [ ] 不同账号登录后看不到彼此的租客、流水、支出、月度账单或匹配记录。
- [ ] TrueLayer refresh token 按账号保存；账号 A 的刷新不会使用账号 B 的 token。
- [ ] 旧 `TL_TOKEN_FILE` 不能在 MySQL 版本中作为跨账号共享 token source。
- [ ] 启动时可以用 `APP_ADMIN_USERNAME` / `APP_ADMIN_PASSWORD` 初始化默认用户。
- [ ] 登录校验来自 MySQL `users` 表；没有注册或用户管理页面。
- [ ] `users` 表只保存 bcrypt password hash，不保存明文密码。
- [ ] refresh token 默认加密保存；live 环境缺少 `BANK_TOKEN_ENCRYPTION_KEY` 时启动失败。
- [ ] 本地只有显式设置 `ALLOW_PLAINTEXT_TOKENS=1` 时才允许明文 token 存储。
- [ ] 数据模型包含可扩展的周期字段，虽然一期只实现月租。
- [ ] 银行交易同步会把归一化交易写入 MySQL。
- [ ] 可以一次性导入已有 `TL_LOG_FILE` JSONL 银行流水到 MySQL。
- [ ] 可以一次性导入已有租客 JSON 和支出 JSON 到 MySQL，或在对应文件不存在时跳过且不报错。
- [ ] 对同一 provider payload 重复同步，不会生成重复可见交易。
- [ ] 月度交租视图能按选中月份展示每个租客的应收、已付、余额和状态。
- [ ] 打开某个月度交租视图时，系统会为该月有效租客懒生成缺失的月租应收记录。
- [ ] 月租应收生成逻辑不是写死在页面 handler 中，后续可以复用为批量生成。
- [ ] 至少一条银行收入交易可以匹配到某个租客的月租应收，并反映到该租客当月已付金额。
- [ ] 已保存付款方 ID 的租客可以通过付款方 ID 自动匹配流水。
- [ ] 未保存付款方 ID 的租客可以通过姓名候选匹配进入人工确认流程。
- [ ] 人工确认后可以把流水付款方 ID 回填到租客，后续同一 ID 可自动匹配。
- [ ] `/billing` 中单一候选匹配可以通过确认按钮创建分配记录。
- [ ] 人工确认时，如果租客缺少付款方 ID 且流水有付款方 ID，系统会回填租客付款方 ID。
- [ ] 多候选交易不会被自动确认，必须保持待审核或未匹配状态。
- [ ] ID 匹配且金额小于应收时，该租客当月状态显示为部分付款。
- [ ] ID 匹配但金额大于应收时，该交易进入待审核，不自动把账单标记为已付。
- [ ] 流水备注中出现明确月份，且对应月份账单未结清时，匹配结果归属到备注月份。
- [ ] 流水备注月份已结清或无法明确识别时，交易进入待审核或按付款日期窗口生成候选，不静默错配。
- [ ] 月份解析测试覆盖数字年月、英文月份、中式月份、无年份月份和冲突/不可识别文本。
- [ ] 未匹配收入交易保持可见并可筛选。
- [ ] 支出/转出交易保持可见并可筛选。
- [ ] 手动支出可以保存 `room_hint` 和 `tenant_hint`，并在支出列表中展示。
- [ ] 支出月度汇总不会改变租客交租状态。

## 一期暂不做

- 多房东组织、角色和权限系统。
- Google 登录和邀请流程。
- 租客门户。
- 发起付款或在线收租。
- 完整会计总账。
- CSV/Excel 导入，除非后续明确拉入一期。
- 复杂租金规则，例如涨租、免租期、水电拆分、多人分摊同一账单。
- 非月租周期的实际账单生成和匹配。
