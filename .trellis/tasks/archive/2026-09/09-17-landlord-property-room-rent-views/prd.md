# 房间入住与租金计划（方案 A）

## 1. 目标

在不向房东暴露“租约管理”心智的前提下，完成以下闭环：

1. 房东从房间详情维护“入住与租金”。
2. 系统按房间、月份生成房间应收和租客个人责任。
3. 租客仍是独立人员档案；进入租客详情可以查看其当前责任和历史责任。
4. 首页继续支持房产、房间、租客三个视角；租客视角可以筛选所选月份未结清的人。
5. 实际付款人和责任人分离，支持同住人代付。

## 2. 已确认的产品决策

- 前台不提供“租约”导航、列表、详情或新建入口。
- 前台统一使用“入住与租金”“当前收租安排”“入住生效月份”等表达。
- 租客是人员与付款识别档案，不是租金配置入口。
- 房间详情是修改房间月租、缴租日、入住成员和责任金额的唯一权威入口。
- 房产和房间不按月份生效或失效；月份边界只属于“入住与租金计划”。房产/房间的当前状态只表示当前资产管理状态，不停止、隐藏或限制租金计划及其事实；结束收租必须通过“结束入住”。
- 后台使用时间化的 `room_rent_plans` 和 `room_rent_plan_members` 保存历史。
- 一个计划是一个完整版本：租金、缴租日或成员责任发生变化，都从指定月份创建新版本。
- 当前只支持整月生效，不做按天折算。
- 系统尚未上线，旧数据均为测试数据；实施时要求清库重建。
- 不实现旧表双读、旧字段回退、历史数据回填、功能开关或旧 URL 兼容。
- 金额口径由界面选择的月份驱动，不固定取机器当前月。
- 逾期日期按 `Europe/Dublin` 判断。

## 3. 核心业务定义

### 3.1 租客

租客仅表示一个自然人及其联系、付款识别信息。租客本身不保存月租、缴租日、房间文本或入住起止日期。

### 3.2 房间入住与租金计划

计划表示某个房间在一个按月生效区间内的完整收租规则，包括：

- 生效月份和可选结束月份；
- 房间月租总额；
- 币种；
- 每月缴租日；
- 入住租客；
- 每位租客的个人责任金额。

### 3.3 月度账务事实

- 房间月应收：一个房间在一个月份的一条总应收。
- 租客月责任：该房间月应收拆给各租客的责任行。
- 不变量：同一房间月份的租客责任合计必须等于房间月应收。
- 首页租客视角一行表示“租客 × 房间 × 月份”的一条责任，而不是简单的一人一行。

### 3.4 付款

- 实际付款人不等于责任人。
- 是否欠租只由责任的未覆盖金额决定。
- 他人已完整覆盖某租客责任时，该租客显示“已缴清 · 他人代付”，不进入未结清或催收名单。
- 一笔付款可分配到多条责任；分配合计不得超过付款可分配余额。

## 4. 用户流程

### 4.1 新建房间

1. 房东填写房间名称、所属房产和备注。
2. 主按钮“保存并设置入住与租金”保存房间后打开房间详情的设置抽屉。
3. 次按钮“仅保存空房间”允许暂时不设置租金计划。

### 4.2 设置入住与租金

1. 在房间详情点击“入住与租金”。
2. 选择生效月份、月租、缴租日和入住租客。
3. 默认可以均分；房东也可以逐人填写不同责任。
4. 系统校验责任合计等于房间月租后保存。
5. 保存成功后，详情和首页均按所选月份读取该版本。

### 4.3 调整安排

- 修改租金、缴租日或成员责任时，从指定月份创建新版本，不覆盖之前月份。
- 只要曾产生付款分配、现金收款、人工平账或催收尝试，该月份就不得重算；后来作废或发送失败也仍保留审计锁。
- 当前月尚无任何财务动作时，允许调整并重建当月应收。
- 未来月份可以预先安排；普通预览不落库。

### 4.4 结束入住

- 房东在房间详情选择“结束入住”。
- 选择“空置生效月份”；房间从所选月份开始空置，上一个月是最后一个仍产生责任的月份。
- 若空置生效月份及之后已经存在任何收款、平账或催收历史（即使后来作废或失败），操作失败并说明被锁定的月份。

### 4.5 查看租客责任

- 租客列表继续一人一条档案。
- 租客详情按月份展示所在房间、个人责任、已覆盖、未付、付款来源和状态。
- 租客详情提供“前往房间调整入住与租金”，但不直接修改全房间计划。

### 4.6 首页查未交租客

1. 选择月份。
2. 切换“租客视角”。
3. 选择状态“未结清”。
4. 列表展示该月份所有 `balance_cents > 0` 的租客责任。
5. 数据异常进入“待核对”，不混入普通未结清名单。

## 5. 首页口径

- “所选月份应收”来自该月份全部有效租客责任。
- “已覆盖”来自有效租金分配（包含银行流水分配和人工平账分配）以及有效现金收款。
- “未结清”表示 `expected_cents - paid_cents > 0`。
- “已逾期”表示未结清，且 `Europe/Dublin` 当地日期晚于应缴日。
- “部分缴纳”表示 `0 < paid_cents < expected_cents`。
- “未缴”表示 `paid_cents = 0` 且尚未逾期。
- “已缴清”表示 `paid_cents >= expected_cents`。
- “待核对”用于账务事实缺失、计划冲突或币种异常，不等同于欠租。
- 筛选值“未结清”只包含未缴、部分缴纳和已逾期，不包含待核对。

## 6. 功能要求

- 一个房间在任意月份最多命中一个有效收租计划。
- 一个计划必须至少有一位成员。
- 成员必须属于当前房东，且同一计划中不可重复。
- 每位成员责任必须大于 0，合计必须严格等于房间月租，精确到分。
- 同一租客在同一个月份最多属于一个房间；保存计划时必须拒绝与其他房间重叠的入住月份。首页有效数据中同一租客同月最多显示一条责任，并显示所属房间。
- 房间物理资料与入住租金计划分开修改。
- 房间一旦已有 rent charge 月度事实，不允许更改所属房产，避免历史责任归属随当前资产关系变化。
- 房产和房间本身不保存生效月、停用月；计划是否命中、能否保存/结束及是否生成责任只由计划时间线决定，资产当前状态不回写或隐藏计划与历史事实。
- 房间没有有效计划时显示“空置”，金额显示 `—`。
- 有有效计划但月度事实缺失或不一致时显示“待核对”，不得显示为空置。
- 当前月及历史月的实际金额均读取月度账务事实；未来月份读取计划预览。
- 页面读取未来月份不得创建账务记录。
- 月度事实生成必须幂等，并发生成只能得到一条房间应收和固定数量的责任行。
- 计划修改、事实生成、付款分配、现金收款和催收尝试对同一房间使用统一锁顺序，计划修改不得与新的财务动作交错穿透锁定检查。
- 房间/房产视角以资产清单为骨架左连接责任汇总，零责任房间仍显示为空置；租客视角才直接以责任行为数据集。
- 每条租客责任必须同时属于同一个 charge、plan 和 plan member，且 `tenant_id` 与 plan member 一致。
- 所有查询和写入均受 `user_id` 隔离。

## 7. 数据重建要求

- 实施前删除并重建本地或测试数据库。
- 新运行时代码只读取 `room_rent_plans` / `room_rent_plan_members`。
- 删除旧 `tenancy_agreements` / `agreement_parties` 运行时模型和仓储方法。
- 删除 `tenants` 上的租金、房间和入住生命周期字段。
- 删除 `properties.inactive_from` 与 `rooms.active_from` / `rooms.inactive_from`；删除 `rooms` 上作为当前值缓存的月租和缴租日字段。
- 不提供旧数据迁移脚本，不保留旧模型 fallback。

## 8. 验收标准

- [ ] 主导航、移动导航和对象页均不出现“租约管理”。
- [ ] `/tenancies` 的 GET 和 POST 均不再注册，返回 404。
- [ ] 新建房间可选择继续设置入住与租金，也可保存为空置房。
- [ ] 房间详情是唯一可编辑月租、缴租日、入住成员和责任金额的位置。
- [ ] 租客新增/编辑只能维护人员档案和付款识别。
- [ ] 租客详情能查看所选月份责任，并能跳转到对应房间设置。
- [ ] 首页保留房产、房间、租客三个视角。
- [ ] 首页租客视角选择“未结清”后，显示所选月份所有余额大于 0 的责任。
- [ ] 一人代付同房另一人的责任后，责任人显示已缴清并标记“他人代付”。
- [ ] 房间月应收等于成员责任之和。
- [ ] 房间已有任一 rent charge 后，更改所属房产返回明确冲突；无月度事实时允许更正所属房产。
- [ ] 房产和房间表单没有生效月、停用月；结束收租只修改房间租金计划时间线。
- [ ] 切换房产/房间 active/inactive 不修改计划或账务事实；inactive 房间仍可维护和结束租金计划。
- [ ] 计划版本不重叠，修改未来月份不会改变过去的账务事实。
- [ ] 当前月无财务动作时可以调整；发生财务动作后返回明确冲突。
- [ ] 未来月份只预览，不因打开页面写入账务事实。
- [ ] 计划修改与并发付款、现金收款或催收竞争时，要么财务动作先完成并锁定计划，要么计划先完成且财务动作基于新责任重试；不得出现审计记录丢失或裸数据库错误。
- [ ] 空置房在房间和房产视角可见并计入房间数量，租客视角不伪造责任行。
- [ ] 迁移和所有 MySQL 集成测试从空库通过。
- [ ] 桌面端和移动端均能完成房间入住与租金设置。

- 跨币种汇总。
- 同一笔付款跨房间的操作界面；底层分配模型不禁止未来扩展。
- 旧测试数据兼容、迁移预览、双读或回滚到旧模型。
- 批量导入 Excel。
