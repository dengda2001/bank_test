# 多目标匹配抽屉：技术设计

## Boundaries and data flow

- 保留 `/transactions` 和 `/rent-dashboard` 的抽屉入口与现有只读核对模型。所选租客仅控制左侧月份证据，不能作为整笔流水唯一归属。
- 可选月卡加入客户端草稿清单，清单以 `(tenant_id, period)` 为键，金额为整数分。切换「查看该租客」及历史分页用同源 GET 获取更新后的服务端 HTML，只替换核对区和历史区，草稿 DOM 与提交表单不重建；失败时保留草稿并显示提示。
- 确认表单提交多组租客、月份、金额及一次请求键到专用批量租金确认入口。服务端重新按 `user_id` 查询来源、租客、责任和实际余额，不信任显示金额或隐藏 ID。
- 每个明确选择的未生成月份通过 `rentFactsIntentExplicitPayment` 生成责任，随后重读月卡；浏览其他租客及历史不会生成未来月份。
- 批量确认复用 `allocateTransactionInTx` 的整批校验、来源锁、责任锁与账本投影。付款人关系若指定某一个租客，在同一事务内保存；提交后沿用现有待匹配流水复核。

## Interaction

1. 左侧选择租客，点「查看该租客」；月份卡保留已入账证据，开放月份显示「加入分配」。同一租客可连续加入多个月份。
2. 下方清单持续显示已有确认分配与本次待确认行。金额默认取该责任未收与本笔可用余额的较小值，用户可改；显示原额、原已分配、本次草稿和提交后余额。
3. 同一租客／月份不能重复加入草稿。金额为正、各目标不超未收、草稿合计不超流水余额才可提交。客户端校验用于即时反馈；服务端始终重新校验。
4. 「记住付款人」初始关闭。启用时必须明确从本次分配的租客中选择一人；分配受益人与银行付款人可以不同。
5. 仅最终确认写分配。部分分配继续显示 `partial`，余额归零显示 `matched`。错误重新打开抽屉并说明余额可能变化；未保存草稿尽量由浏览器保留，以便修改重试。

## Compatibility and risks

- `/transactions/confirm` 的单目标入口供其他页面继续使用；新批量入口只服务核对抽屉。
- 现有部分匹配保留原分配记录，新批次仅追加；原始流水不修改。已有分配需要纠错时使用审计撤销流程。
- 多月未来责任只能由明确的付款月份选择触发生成，防止普通浏览提前开账。
- CSS 与模板采用现有抽屉基元；桌面证据与历史双列，手机单列，底部汇总和确认保持可达。
