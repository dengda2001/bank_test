# 房东收租工作台（父任务）

## 目标

把现有 RentOps 从“查看银行流水、按单笔匹配”完善为可追溯的月度收租闭环：房东能按账单月份查看应收、实收和未收；确认银行或现金收款的归属；找出需处理流水；并向选定单个月份的欠款租客发送可核对的邮件催缴。

本文件是用户于 2026-09-15 提供的《房东收租工作台总 PRD v0.33》的可执行父任务索引。原 PRD 的需求编号、决定、边界和 AC-01～AC-111 是本任务的规范来源；本文件不改变已确认的产品决定，只将其分配给可以独立验收的子任务。

## 已确认的产品边界

- 使用者是房东；保留现有登录用户的数据隔离。没有租客自助门户、团队权限或多房东 SaaS。
- 一张有效租金账单对应一位租客、一个租金所属月份；实收只由有效银行房租分配和有效现金补录组成。银行到账月份只用于流水／其他收入统计。
- 一期只支持 EUR（欧元）收租和汇总；数据库保留三位币种字段、服务边界仍做币种校验，为后续多币种扩展留口子。不做换汇或跨币种相加。
- 银行入账用途固定为房租、押金、其他收入；“无需匹配”是处理结果，不是第四种用途。押金不计房租实收或其他收入。
- 一笔银行流水只能关联一位租客，但可在该租客内跨月、跨用途拆分；可以保留未分配余款、续配，或整体撤销后重新匹配。跨租客拆分不在一期。
- 现金只支持单月租金补录及有原因的作废；不支持现金多月拆分、退款、预存款或通用手工收款。
- 租期与月份有交集即整月收费；租金版本、准确历史价格补建、独立房间、换房历史、押金台账与跨月欠款总览后置。
- 逾期是未结清账单的附加状态，按 `Europe/Dublin` 本地日历日、应缴日次日起算；历史页展示截至当前的结清状态，不提供历史时点快照。
- 催缴抽屉一次只处理其选择器中的一个账单月份，可选历史、当前或未来适用月份；一期英文固定模板、当前页批量选择、人工发送。当天成功催缴默认不选，但可二次确认重发。
- 自动入账只能在付款人唯一、备注明确唯一月份、币种一致、金额不超过该月未收、且不存在冲突时发生；否则至多关联租客并保留待处理。

## 基线事实

- 当前 MySQL 模型已有 `tenants`、`rent_obligations`、`payment_transactions`、`payment_allocations`；但一笔流水只能整笔匹配一张账单，且无用途、可逆审计、现金或邮件记录。
- 当前页面已有 `/rent-dashboard`、`/billing`、`/tenants`，但租客历史只显示近三个月、流水筛选有限、没有现金或催缴。
- 现有后续刷新窗口为最近 90 天；首次授权可以通过 `TL_FROM` 请求更长历史范围。已保存流水不会因后续窗口缩短而删除。
- 现有日期计算多处使用 UTC；必须在账单到期、逾期和“今日已发送”路径统一改为 Dublin 日历口径。

## 跨子任务验收

- 同一笔钱在所有视图仅按有效分配计一次：`原流水金额 = 有效房租 + 有效押金 + 有效其他收入 + 未分配余额`；整笔无需匹配不进入任何用途金额。
- 9 月收到的钱确认用于 8 月时，8 月实收增加，9 月银行到账流水仍可查，9 月租金实收不被伪造增加。
- 银行 €600 与现金 €400 共同缴清同一 €1,000 账单；历史、Dashboard 和催缴在同一次读取中都显示已缴清，并分别展示来源。
- 任何撤销／作废只能撤回它自身曾贡献的有效金额；银行原文不变，现金和银行彼此不误扣，重复请求不二次变更。
- 用户隔离覆盖链接、筛选、详情、补录、撤销、重配和发信；其他用户的 ID 不能泄露信息、改变金额或触发邮件。
- 一期所有有效账单、收款和 Dashboard 金额必须为 EUR；筛选和分页不可改变全月金额、笔数或人数口径；Dublin 日期规则必须在账单、逾期和催缴去重一致。非 EUR 输入要被明确拒绝或保留为待处理，不得静默换算。

## 产品审查结论

总 PRD 的用户价值、边界和验收场景已充分收敛，适合进入“分任务规划”，不适合直接作为一个实现任务。最重要的合理性调整是先实现共享的可审计账本，而不是让每个页面各自计算收款；否则跨月拆分、现金作废、Dashboard 和催缴会产生不一致。

以下是实施前必须在各子任务 `design.md` 中落定的技术／运营准备项，不重新打开已确认的产品范围：

1. **一年历史同步的可验证定义**：明确滚动 365 天或自然月份、每个授权账户的分页／失败边界、成功覆盖区间和页面展示。现有 `TL_FROM` 只是一项请求参数，不能证明服务实际返回完整一年。
2. **邮件投递接入**：PRD 已规定显示名、Reply-To 和记录语义，但仓库没有邮件服务或凭据。第 6 项开始前需由房东提供可用投递服务／测试收件人，或明确批准所选服务。
3. **迁移与并发策略**：现有 `payment_allocations` 的唯一键限制“流水 × 账单”只允许一项，无法容纳混合用途、整体撤销审计和重试键。第 1 项必须先设计向后兼容迁移、锁／条件更新与回滚方案；EUR-only 不能演变成删除币种字段或阻断后续扩展。
