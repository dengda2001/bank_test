# 简化账单与租约的自动收租方案

## Goal

把 RentOps 从“房东分别维护房间、租约和账单”简化为“房东只维护房间与租客入住关系，系统自动形成租住安排和月度应收责任”。房东仍能可靠地查看应收、实收、未收、匹配流水、现金收款和催收，但不需要理解或手工创建账务技术实体。

## User Value

- 新增一个租客时，在同一处完成资料、房间、入住时间和责任金额设置，不再跳到租约页重复录入。
- 房间月租是房东理解的总租金；多人同住时默认均分，也允许在需要时明确不等分。
- 每月应收由系统自动生成；房东处理的是“谁还没交”和“这笔钱属于谁”，而不是维护账单生命周期。
- 后续涨租、换房或退租不会改写已经发生的历史月份、付款和催收记录。

## Confirmed Product Decisions

- 保留现有 `tenancy_agreements`、`agreement_parties`、`rent_charges` 和 `rent_obligations` 的底层职责；本任务不通过删除账务事实来换取表面简化。
- 房东不单独创建或维护租约。租客新增／编辑是入住配置入口，系统自动生成或更新内部租住安排。
- 房间保存对用户可见的月租总额和缴租日；租客责任合计必须精确等于房间月租。
- 多人同住默认按人数均分，余数使用稳定规则分配；房东可按人改写责任金额，后端必须再次校验金额守恒。
- 租客可以先只保存人员资料而不绑定房间；未绑定前不产生结构化月度应收或催收候选。
- 一个租客在同一账单月最多绑定一个房间；多人可以绑定同一房间。
- 入住、退租、换房、涨租和责任调整按整月生效，不做月中按天折算。
- 既有旧租客、旧账单、付款分配、现金收款和催收记录继续可读；本任务不从旧文本地址猜测房产／房间关系，也不批量重写历史。
- 底层必须继续区分：租住规则、房间月度总应收、租客个人责任、实际付款以及付款分配。
- 独立“应收账单”从桌面主导航和手机底部导航移除；其月度责任列表与操作收拢到“月度工作台 → 租客视角”，旧 `/bills` GET 路由保留兼容跳转。
- 未来月份允许接收预付房租，但单纯浏览未来月份只显示预测，不固化或锁定安排；月份开始，或用户明确把一笔付款分配到该未来月份时，系统才生成稳定的月度总应收和个人责任。

## Repository Facts

- `rooms` 已有 `monthly_rent_cents` 和 `due_day`；`tenancy_agreements` 与 `agreement_parties` 已能表达带时间范围的房间租金和多人责任。
- 租客绑定房间时已有自动写租住安排的路径，但当前表单仍同时暴露租客月租、房间、计费开始日、应缴日和旧文本房间字段，用户心智和事实来源尚未收敛。
- 当前存在两套月度应收生成路径：旧路径从 `tenants.monthly_rent_cents` 懒生成；新路径可从租住安排生成 `rent_charge` 和个人责任，但尚未接入统一的生产调用链。
- `/bills/generate` 仍调用旧租客生成器；结构化租客创建时又会把租客自身月租置为零，存在“已有房间安排但没有月度责任”的断层风险。
- 付款分配、现金收款、人工平账、催收尝试和租客缴费历史都依赖 `rent_obligations`，因此月度责任不能删除或只在页面临时计算。
- 月度工作台已有房产、房间和租客三个视角，能够承载当前独立账单页的大部分读取与操作能力。
- 工作台的一键平账、交易详情和若干兼容链接仍直接引用 `/bills` 路由，隐藏页面前必须迁移动作与返回上下文。

## Requirements

### R1. 单一房东配置入口

- 房间表单只负责房产归属、房间资料、月租总额、缴租日和生效月份。
- 租客表单负责人员资料、付款识别以及可选入住配置；选择房间后显示该房间总租金、当前／目标月份的全部入住人和责任分配。
- 不再提供第二套“新建租约”或“编辑租约”表单。
- 编辑租客不得继续要求重复维护旧文本房间地址、房间名称、个人应缴日和房间总租金等兼容字段；兼容数据只能由服务同步或以只读方式显示。

### R2. 自动版本化租住安排

- 新增、换房、退租、涨租或责任调整通过一个领域服务写入完整的下一版本安排。
- 写入必须在一个事务中关闭被替换的安排、创建新安排及全部参与人责任，不能留下部分成员或金额不守恒的中间状态。
- 已生成且已经进入账务流程的历史月份不可原地重写；更正继续使用现有作废／调整审计机制。
- 空房间可以保存月租规则，但没有有效参与人时不得产生个人应收。

### R3. 统一月度应收生成

- 建立唯一的“确保某用户某月份租金事实完整”服务：对结构化房间使用有效租住安排生成一个房间月度 `rent_charge` 和多条租客责任；对仍在兼容期的旧租客保留受控的 legacy 生成路径。
- 同一房间同一月份最多一条有效总应收；同一总应收下同一租客最多一条责任；重复访问、重复生成和并发调用均不得重复记账。
- 结构化租客不得再依赖 `tenants.monthly_rent_cents` 生成月度责任。
- 月度工作台、租客历史、流水匹配候选、现金收款和催收必须读取同一套已持久化责任事实。
- 房东不需要点击“生成本月账单”；需要账务事实的正常业务入口负责安全地确保事实存在。

### R4. 精简信息架构和术语

- 面向房东优先使用“入住与分担”“本月应收”“个人责任”“已收／未收”，不把内部 `agreement`、`charge`、`obligation` 直接翻译成多套需要维护的对象。
- “租约管理”不再是独立可写模块；历史租住安排如保留，只能作为房间／租客详情中的只读历史。
- 独立“应收账单”页不再作为用户产品页面；月度责任列表、状态和操作收拢到月度工作台租客视角，且不得存在手工创建账单入口。
- 所有从旧 URL、书签和详情链接进入的请求必须得到兼容重定向或等价读取页面，不能直接 404。

### R5. 操作入口连续性

- 流水匹配、拆分、撤销、现金补录、人工平账、催收和租客缴费历史继续工作，并继续关联稳定的个人责任 ID。
- 工作台操作不再提交到会把用户带回隐藏页面的 `/bills` 专属流程；规范动作路径和 `return_to` 必须回到原工作台上下文。
- 交易详情对责任的回溯应进入对应租客／房间／月份，而不是依赖独立账单页存在。
- 已确认付款、现金和催收审计记录不得因页面精简被删除、孤立或重新归属。

### R6. 兼容与迁移

- 数据库迁移遵循只增不破坏；不删除现有表、旧字段或外键。
- legacy 与结构化记录必须有明确识别条件，避免同一租客同一月份同时生成旧责任和新责任。
- 现有 `/bills`、`/bills/settle`、`/tenancies` 等路径先保留兼容行为；确认没有内部消费者后才能在后续任务移除代码。
- 本任务不负责把所有旧租客自动迁移到结构化房间，也不根据姓名、房间文本或地址猜测关系。

## Acceptance Criteria

- [ ] 房东创建房间时只设置一份房间月租和缴租日；创建租客并选房间后，无需进入租约或账单页面即可完成入住配置。
- [ ] 单人入住自动承担全部房租；多人入住默认均分；手工不等分有效；责任合计不等于房租时保存被拒绝且事务无残留。
- [ ] 未绑定房间的租客不生成结构化应收；绑定后从指定整月边界生效。
- [ ] 当前或历史月份第一次进入工作台／匹配流程时，结构化房间自动形成唯一的房间总应收和个人责任；重复访问与并发不重复生成。
- [ ] 同一结构化租客不会同时得到 legacy lazy obligation 和 rent-charge obligation。
- [ ] 涨租、换房、退租或修改分担不会改变已生成历史月份的金额、责任人、付款分配、现金收款或催收记录。
- [ ] 月度工作台、房间详情、租客详情、流水匹配、现金收款和催收对同一月份显示一致的应收、已收、未收与状态。
- [ ] 主导航不再要求房东先后维护“房间→租约→账单”；所有核心收租动作仍有明确入口。
- [ ] 旧 `/bills`、`/tenancies` 深链和既有 POST 动作有兼容重定向或别名，旧书签与内部链接不出现 404。
- [ ] 旧租客和历史账务保持可读，未进行基于文本字段的自动关系推断。
- [ ] 相关 Go 单元测试、MySQL 迁移／集成测试、路由测试和桌面／移动浏览器验收通过。

## Out of Scope

- 删除账务表、清空历史账单或把所有金额改成按页面实时计算。
- 旧文本租客资料的自动迁移或批量修复。
- 月中按天计租、免租期、阶梯租金、水电杂费、押金台账或多币种换汇。
- 租客自助门户、电子签约、合同文件上传或法律意义上的租约管理。
- 同一租客同一月份承担多个房间。
