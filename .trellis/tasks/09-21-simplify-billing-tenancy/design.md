# 设计：房间与租客驱动的自动收租

## 1. 设计结论

采用“产品模型收敛、账务模型保留”的方案：

```text
房东可见
Property → Room（月租、缴租日） → Occupants（入住人、分担、生效月）
                                      ↓ 系统自动
后台事实
tenancy_agreement + agreement_parties
                                      ↓ 月度固化
rent_charge（房间/月总应收） → rent_obligations（租客个人责任）
                                      ↓
payment_allocations / cash_receipts / dunning attempts
```

房东只维护房间和租客入住。`tenancyAgreement` 不再代表需要用户管理的“合同页面”，而是房间租金与成员分担的内部版本；`rentCharge` 和 `rentObligation` 是不可缺少的月度账务事实，但由系统生成。

不采用把全部金额压回 `rooms` 和当前租客关系的方案，因为它无法稳定表达历史租金、换房、多人不等分、补交所属月份、付款分配和催收审计。

## 2. 事实所有权

### 2.1 Room

- 用户可见的当前／下一生效月租总额和缴租日。
- 不保存某个租客个人应付金额。
- 允许空房间存在租金规则；空房没有个人责任。

### 2.2 Internal Rent Arrangement

- 继续由 `tenancy_agreements` 与 `agreement_parties` 承载。
- `tenancy_agreements` 保存房间、整月有效范围、总月租、币种和缴租日。
- `agreement_parties` 保存该版本中的租客和明确责任金额。
- 每次成员、总租金、缴租日或分担变化都创建新版本，不原地改写已使用版本。
- 对用户使用“入住与分担”术语；代码表名暂不重命名，避免无收益的大迁移。

### 2.3 Monthly Ledger Facts

- `rent_charges` 是房间 × 月份的总应收快照，保留房产、房间、安排和显示名称快照。
- `rent_obligations` 是 `rent_charge` 下的租客个人责任，是银行分配、现金、平账和催收的稳定目标。
- `rent_obligations.rent_charge_id IS NULL` 只代表 legacy 兼容责任；新结构化数据必须有 `rent_charge_id`。

## 3. 写入边界

新增／收敛为一个领域命令（名称可在实现时按现有代码风格调整）：

```go
type SaveRoomOccupancyPlanInput struct {
    UserID          uint64
    RoomID          uint64
    EffectiveMonth  time.Time
    ContractDate    *time.Time
    MoveInDate      *time.Time
    EndDate         *time.Time
    MonthlyRentCents int64
    DueDay          int
    Responsibilities []RentResponsibilityInput
}
```

事务内执行：

1. 锁定用户、房产、房间和目标月份覆盖的当前安排。
2. 验证房产／房间有效、租客归属当前用户、同月不在其他房间。
3. 若仅提供成员列表，按稳定租客 ID 顺序均分；若提供金额，严格校验每项为正且总和等于房间月租。
4. 检查目标月份是否已存在不可改写的月度事实或有效付款；冲突时返回可识别错误。
5. 将旧版本截止到生效月前一天，创建新安排和完整 party 集合。
6. 同步 `rooms.monthly_rent_cents`／`due_day` 作为当前显示默认值；不再把结构化个人责任写回 `tenants.monthly_rent_cents` 作为生成来源。

租客表单和房间编辑都调用同一命令，不能各自直接修改安排表。

## 4. 月度事实生成

### 4.1 统一服务

建立 `EnsureMonthlyRentFacts(userID, periodMonth)` 编排器：

1. 查询该用户目标月份内的有效房产、房间、唯一安排和有效参与人。
2. 对有参与人的结构化房间调用/复用 `ensureRentCharge`，生成一条 charge 和完整 obligations。
3. 对未进入结构化模型的 legacy 租客调用收窄后的 lazy generator。
4. 在一次读取结果中返回生成失败的房间／原因，使页面显示“待处理”，不能把缺责任误判为空置。

唯一性继续由数据库与服务共同保证：

- `rent_charges(user_id, room_id, period_month)` 唯一。
- `rent_obligations(user_id, rent_charge_id, tenant_id)` 唯一。
- legacy `(user_id, tenant_id, period_month)` 唯一，并且生成器必须排除目标月存在有效结构化安排的租客。

### 4.2 调用点

- 月度工作台、房间详情、租客历史、账务匹配候选、现金录入和催收候选在读取目标月份前调用同一确保服务。
- “生成本月账单”按钮删除；重复访问自然幂等。
- 新增／修改安排后不批量生成所有未来月份，只保存规则。当前／历史月份在读取时固化；未来月份普通读取只生成预测，月份开始或明确分配预付款时才固化。

### 4.3 错误处理

- 多个重叠安排、责任不守恒、跨用户租客或币种不支持时，不生成半组责任。
- 工作台将“有安排但生成失败”显示为待处理，并给出可操作原因。
- 不回退到读取 `rooms.monthly_rent_cents × 人数` 临时拼金额。

## 5. 页面与路由设计

### 5.1 导航

推荐的信息架构：

- 收租：首页（月度工作台）、流水、催收。
- 对象：房产、房间、租客。
- 系统：银行；现金和支出保留现有可达入口。
- 不显示“租约管理”主导航。
- 不显示独立“应收账单”导航；其读取和操作收拢进月度工作台的租客视角。

### 5.2 房间

- 新建／编辑：房产、房间名称、月租总额、缴租日、生效月份和备注。
- 详情增加“入住与分担”：当前入住人、个人责任、开始／结束月份，以及新增／移出成员入口。
- 修改月租时展示调整后完整分担；默认按现有比例缩放，允许一键均分和逐项修改。

### 5.3 租客

- 表单分为“租客资料”“付款识别”“入住与分担”三组。
- 选择房间后使用房间月租和缴租日，不再要求重复输入一份个人月租和应缴日。
- 加入已有住客的房间时，显示保存后该房间全部人的责任预览；默认均分，可展开高级分担编辑。
- 解绑／换房必须选择生效月份并展示旧、新房间的影响。
- legacy 文本字段仅在旧记录兼容读取时显示，不作为新记录的必填输入。

### 5.4 账单与租住历史兼容

已确认的兼容方案：

- `/bills?period=...` 302 到 `/rent-dashboard?view=tenants&period=...`，保留能映射的筛选参数。
- `/tenancies` 302 到 `/rooms`，或在房间／租客详情提供只读历史；不再有新增租约按钮。
- `/rent-dashboard/settle` 成为规范人工平账动作；`/bills/settle` 保留兼容别名但使用显式 `return_to`，不再强制回到账单页。
- 交易详情的“对应账单”改为“对应责任”，链接到租客／房间详情的目标月份。
- 旧书签和外部深链在至少一个兼容周期内不返回 404。

## 6. 兼容迁移

- 不删除旧字段或表；先通过写入规则让新结构化记录不再产生 legacy 月租。
- 为结构化租客定义明确判断：目标月存在有效 `agreement_party + tenancy_agreement` 即由 rent-charge 路径负责，legacy generator 必须跳过。
- 已有 `rent_charge_id IS NULL` 的历史责任保持原 ID 和全部付款／现金／催收引用。
- 如发现同一租客同月已有 legacy responsibility 与待生成结构化责任，停止自动生成并标记待处理；不静默合并有资金引用的数据。
- 路由迁移先加规范路径和兼容别名，再改内部链接，最后才考虑删除旧页面模板。

## 7. 未来月份与预付款

已确认策略：

- 当前月和历史月：首次业务读取时持久化，随后保持历史稳定。
- 未来月：默认显示由安排计算的预测，不因浏览页面就锁定；当用户明确把付款分配到该未来月时再固化该月责任。
- 未来预测不能进入催收、人工平账或已收统计；这些操作要求先通过明确的付款归属形成持久化责任。
- 一旦未来责任因预付款被固化，该月份的租金和责任人按历史保护规则锁定；后续更正必须走审计型调整，不能静默重算。

## 8. 风险与回滚

- 最大账务风险是 dual-write：同一结构化租客同时被 legacy 和 rent-charge 两条路径生成。先用测试和查询守卫阻断，再切页面。
- 最大产品风险是隐藏页面后丢失平账、现金或责任回溯入口。必须先把动作迁到工作台／详情并完成浏览器验收，再移除导航。
- 最大历史风险是删除或重建 obligation 造成付款、现金和催收级联删除。方案明确不删除已有责任。
- 回滚时可恢复旧导航和 GET 页面；新增统一生成服务可通过调用点回退，数据库事实和旧路由保持兼容。

## 9. 验证矩阵

- 领域：单人、多人均分、不等分、涨租、换房、退租、空房、重叠安排、金额不守恒。
- 账务：重复生成、并发生成、legacy 排除、付款／现金／催收引用保持、历史月份不漂移。
- HTTP：旧路由重定向、POST 别名、`return_to`、筛选与月份保留、其他用户 ID 拒绝。
- UI：桌面和 360/390/430px 手机完成新增租客→选房→查看当月责任→匹配／平账的主流程。
- 数据：空库迁移与含旧 obligation、allocation、cash receipt、dunning attempt 的升级验证。
