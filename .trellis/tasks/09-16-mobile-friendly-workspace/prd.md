# PRD：移动端友好版 RentOps 工作台

状态：规划草案（推荐方案）
目标用户：房东／收租运营人员
目标设备：手机优先，兼容平板和桌面浏览器
关联任务：`09-16-mobile-responsive-audit`

## 1. 背景

RentOps 当前已经具备一轮移动端基础适配：共享导航抽屉、表格滚动容器、移动端冻结操作列、较大的触控区域，以及针对窄屏的 Go 回归测试。但主要业务页仍沿用桌面表格的信息架构。手机上虽然“能打开”，但流水匹配、租客管理、租金总览等核心任务仍需要横向寻找字段，信息密度高，页面较长，部分操作的主次关系不清晰。

之前的真实浏览器审计覆盖了 10 个页面，并确认了以下事实：

- 页面级横向溢出已经基本消除，但表格内部仍有较大的横向滚动距离。
- `/billing` 是最复杂的页面：筛选项多、每行操作多、金额和匹配信息需要同时阅读。
- `/tenants`、`/rent-dashboard`、`/expenses` 的数据行包含过多字段，手机上容易形成高行和长页面。
- 表格横向滚动适合作为桌面／平板的补充方式，不适合作为手机端主要的信息浏览方式。
- 当前代码、模板和测试均位于 `cmd/truelayer-demo/`，服务端数据和路由已经可支持这次 UI 重构，不需要先做后端重写。

## 2. 问题定义

手机用户需要在碎片时间完成以下动作：

1. 快速判断本月哪些租客未缴、欠款多少。
2. 查看一笔银行流水是谁的、金额是多少、是否已匹配。
3. 直接完成匹配、归类、忽略或撤销操作。
4. 添加／编辑租客、录入现金收款和支出。
5. 在网络较慢、屏幕较小、单手操作的情况下，不被横向滚动、错位表单或屏外按钮阻塞。

当前界面的问题不是单纯的“宽度不够”，而是桌面端的字段组织方式没有针对移动端任务重排。

## 3. 产品目标

### 3.0 最高优先级原则：少打扰、少操作、少记忆

产品服务的是拥有很多房产、日常事务繁忙的房东。页面不是用来展示所有系统能力，而是帮助房东快速完成当前最重要的事情。因此所有页面和功能必须遵循：

- 首屏只显示当前决策所需的信息。
- 默认状态只保留一个主要动作，最多一个次要动作。
- 能自动判断、自动汇总、自动保留的内容，不要求用户重复选择。
- 低频字段、技术字段和复杂操作默认隐藏，不在首屏制造负担。
- 用户应尽量通过“看一眼 → 点一下”完成任务，而不是阅读表格、组合多个筛选条件或记住处理流程。
- 页面宁可少展示一些信息，也不能让用户面对一整页控件后自己判断先做什么。

任何新功能如果会增加首屏信息、按钮数量、必填字段或用户需要记忆的规则，必须证明它能减少后续操作，否则不纳入移动端默认流程。

### 3.0.1 移动端禁止“大表格”

手机端不是把桌面表格缩小，也不是把大表格放进横向滚动容器。对 320～412px 的手机视口：

- `/rent-dashboard`、`/billing`、`/tenants`、`/expenses` 等核心页面不得渲染宽表格作为主要内容。
- 用户不得通过横向滑动来寻找租客姓名、金额、状态、详情或操作按钮。
- 数据列表必须使用卡片、分组列表、折叠详情或步骤化内容呈现。
- 金额、状态、对象身份和主要操作必须在同一个手机视图上下文中出现。
- 历史记录即使字段较多，也必须优先使用纵向账单卡片；不以“支持横向滚动”作为移动端完成标准。
- 只有明确的技术明细、导出预览等非日常场景，才可以在独立详情区域使用横向滚动，并且不能影响页面主流程。

这条是阻断条件：只要核心页面仍依赖大表格横向滚动，就不能宣布移动端改造完成。

### 3.1 核心目标

把 RentOps 改造成“手机上可完成核心收租工作”的响应式工作台：

- 手机端优先展示业务结论和下一步操作。
- 复杂数据使用卡片摘要 + 就地展开详情，而不是强迫用户先横向找列。
- 筛选、表单和操作入口按任务优先级重排。
- 保留桌面端表格效率，不改变现有业务语义、路由和数据模型。
- 所有页面在真实浏览器中经过多视口、多状态、交互和截图验证。

### 3.2 非目标

- 不开发原生 App、PWA 或离线能力。
- 不改变租金匹配、收款、支出和催缴的业务规则。
- 不修改数据库 schema、API 路由或权限模型，除非实现中发现现有页面无法表达必要状态。
- 不为了移动端而删除桌面端表格能力。
- 不把所有页面强行统一成完全相同的卡片样式；页面应按业务任务使用合适的移动布局。

## 4. 设计原则

1. **任务优先于字段完整性**：手机首屏先展示“谁、多少钱、什么状态、下一步做什么”。
2. **身份与操作必须同屏**：用户点击匹配、编辑或作废时，必须能确认当前对象是谁。
3. **渐进披露**：次要信息和复杂表单默认收起，点击后就地展开，不跳到难以返回的横向位置。
4. **桌面／手机两种阅读模式**：桌面保留表格，手机切换为卡片或折叠列表，不要求同一 DOM 结构承担两种密度。
5. **状态可识别**：不能只依靠颜色；状态必须有文字，金额、方向和错误也要有明确标签。
6. **单手可操作**：关键按钮和表单控件触控命中区至少 44×44px，主操作在卡片底部或右侧稳定位置。
7. **真实数据优先验证**：长姓名、长地址、英文银行描述、空状态、错误状态和大量列表必须纳入验收。
8. **默认简单，复杂可选**：完整能力可以存在，但不能以完整能力的形式出现在默认界面。

## 5. 用户故事与验收结果

### 5.1 月度收租

作为房东，我打开月度总览后，希望在一个屏幕内看到本月收款概况，并能快速定位未缴或需处理的租客。

验收结果：

- 汇总指标在手机上优先展示：应收、已收、未收、待处理。
- 租客列表卡片首屏展示姓名、房间／地址摘要、应收、已收、未收和状态。
- “查看租客详情”和“展开缴费明细”是两个可区分的操作。
- 默认只突出“查看未缴／待处理”，已缴租客和完整历史通过筛选或展开查看。
- 页面打开后应自动使用当前月份和默认优先级，不要求房东先配置筛选条件。
- 卡片内的平账、催缴入口可见且不需要横向滚动。
- 排序、月份切换和状态筛选在手机上不会被挤压或折成竖排文字。

### 5.2 银行流水处理

作为房东，我希望在手机上核对每笔流水并完成匹配，而不是只能查看流水。

验收结果：

- 每笔流水的移动摘要至少包括：收入／支出、付款人或描述、金额、到账日期、匹配状态。
- 匹配、选择租金月份、归类／拆分、忽略、撤销等动作在当前流水卡片内完成。
- 默认只显示“待处理”流水；已完成和已忽略流水通过切换查看，不和待办事项混在一起。
- 系统能根据付款人、金额和月份给出默认建议，房东只需确认，不要求重复填写已知信息。
- 复杂操作默认收起，展开后表单单列排列，按钮不被挤出视口。
- 金额必须完整显示，不能被裁切成看似合法但不准确的数字。
- 用户可以通过“更多筛选”访问完整筛选条件，筛选后返回仍保留当前条件。

### 5.3 租客管理

作为房东，我希望快速查看租客资料并进入详情或编辑，而不需要在表格最右侧寻找按钮。

验收结果：

- 手机端每个租客以卡片显示姓名、付款人、月租、房间摘要和状态。
- 详情、编辑是稳定可见的操作，不依赖横向滚动。
- 地址、账单安排、创建时间等次要信息允许折叠，但不能逐字断裂或破坏卡片高度。
- 添加／编辑表单在 320px 宽度下仍为单列，提交按钮全宽或占据明确主操作位置。

### 5.4 支出记录

作为房东，我希望快速录入一笔支出并查看近期支出。

验收结果：

- 录入表单在手机端按“描述、金额、日期、类别、支付方式、关联租客／房间、备注”的任务顺序排列。
- 金额使用数字键盘，日期使用日期控件，币种字段明确标识为只读。
- 支出列表卡片首屏展示日期、描述、金额、类别；备注和支付方式作为次级信息。
- “保存支出”在窄屏下为清晰的主按钮，不能被其他操作抢占视觉层级。

### 5.5 现金收款和纠正

作为房东，我希望在手机上录入现金收款，确认预览，并在需要时安全作废。

验收结果：

- 现金补录表单打开后，首个可填写控件出现在首屏可见区域。
- 预览页明确区分当前已收、本次现金和入账后未收。
- 作废页先展示不可逆影响和收款事实，再展示原因输入和确认按钮。
- 危险操作按钮在手机上有明确颜色、文字和足够大的点击区。

## 6. 页面范围和目标形态

### 6.1 共享工作台外壳

- 手机端使用顶部紧凑导航栏 + 抽屉导航。
- 当前页面标题、返回路径和主操作在顶部稳定可见。
- 退出登录、导入旧数据、历史付款人预览等低频操作移入次级操作区或页面菜单。
- 抽屉打开时有遮罩，关闭时不应把隐藏链接留在键盘 Tab 顺序中。

### 6.2 `/rent-dashboard`

- 桌面端：保留当前表格和汇总布局。
- 手机端：汇总卡片 + 租客卡片列表。
- 卡片默认折叠付款明细；展开后显示付款记录和操作。
- 月份切换使用明确的上一月、月份、下一月三段布局。
- 默认进入当前月份和“待处理优先”，筛选区不要求用户先操作。
- 搜索、状态是两个核心条件；排序、每页条数和历史范围进入更多筛选／列表工具栏。

### 6.3 `/billing`

- 桌面端：保留当前交易表格。
- 手机端：交易卡片流，不以 680px 以上的横向表格作为主要浏览方式。
- 卡片摘要：方向、付款人／描述、金额、到账日期、匹配状态。
- 卡片展开区：匹配、租金月份选择、归类拆分、忽略、恢复、撤销等动作。
- 默认列表只展示待处理流水，并按“最可能需要房东处理”的顺序排列。
- 已匹配流水不在默认列表中占据注意力；查看完整流水是次级入口。
- 筛选区分为：
  - 首要筛选：付款人搜索、到账月份、匹配状态。
  - 更多筛选：租客、租金所属月、入账用途、收支方向、日期范围、排序。
- 所有筛选条件保存在 URL，刷新、分页和返回列表后不丢失。
- 金额、匹配状态和动作必须在同一个卡片上下文内可见。

### 6.4 `/tenants`

- 桌面端：保留完整表格。
- 手机端：租客卡片列表。
- 卡片主信息：姓名、房间／地址摘要、月租。
- 卡片操作：详情、编辑、展开账单历史。
- 默认优先显示欠款或需要处理的租客；已正常缴费的租客可以收起或放到次级列表。
- 地址和账单安排超过可读长度时使用截断 + 展开，而不是逐字换行。

### 6.5 `/tenants/:id`

- 档案信息由两列标签布局改为手机单列信息组。
- 付款人关系保持卡片化，每条关系的移除按钮固定在条目内。
- 缴费历史手机端使用账单卡片；平板及以上可保留表格。
- 起止月份筛选在手机上单列，两个控件宽度一致。

### 6.6 `/expenses`

- 桌面端：保留表格。
- 手机端：支出卡片列表。
- 录入表单单列化，提交按钮通栏。
- 列表卡片默认隐藏低频的内部 ID、备注和支付方式，展开后查看。

### 6.7 `/cash-receipts/new`、`/cash-receipts/void`

- 保留现有服务端提交和预览流程。
- 统一表单间距、控件高度、只读字段样式和危险操作样式。
- 移动端不允许任何字段或按钮超出内容区。

### 6.8 预览页

- `/billing/revoke` 和 `/billing/payer/preview` 的标题、说明、返回入口必须固定在卡片可见区域。
- 只有内部宽内容区域允许横向滚动，禁止整张页面卡片横向滚动。
- 两个预览页的关键按钮和原因输入框必须达到移动端点击尺寸。

### 6.9 登录页

- 保持单列、通栏输入和按钮。
- 覆盖 320px 宽度、错误提示和键盘弹出后的可用性。

## 7. 筛选与表单规范

### 7.1 筛选

- 手机默认只展示不超过 3 个最高频筛选项。
- 页面首次打开时应使用合理默认值，不能要求用户通过筛选器才能看到有用内容。
- 其余条件由“更多筛选”按钮打开抽屉、折叠面板或就地展开区。
- 打开更多筛选时不改变页面滚动位置，关闭后保留已选值。
- 应用筛选和清除筛选必须是两个清晰、尺寸足够的操作。
- 筛选条件、排序、分页全部通过 URL 可复现。
- 空筛选结果必须提供“清除筛选”入口。

### 7.2 表单

- 手机端默认单列，标签位于控件上方。
- 输入、选择、日期、按钮的可见点击区至少 44×44px。
- 货币金额使用 `inputmode="decimal"`；日期和月份使用语义化 input type。
- 只读字段使用不同于可编辑字段的视觉样式。
- 主提交按钮通栏或占据明显主操作位置；取消／返回为次级按钮。
- 错误信息显示在相关字段附近，同时保留页面级错误提示。
- 长文本、英文银行描述、中文地址和付款人 ID 使用可读换行规则，不允许逐字符竖排。

## 8. 视觉与交互要求

- 采用当前项目已有的浅色、低装饰、边框分组视觉，不引入新的渐变、重阴影或完全不同的品牌色。
- 页面标题、区块标题、主数据和辅助信息建立稳定层级。
- 首屏不同时展示多个同等级主按钮；每个页面必须有明确的“现在最该做什么”。
- 已完成、已读或低优先级信息降低视觉权重，不与待处理事项争夺注意力。
- 关键状态必须同时使用文字和颜色；金额正负也必须有文字语义或方向标签。
- 卡片圆角、间距、按钮高度和表单间距使用统一设计 token。
- 支持键盘 Tab、Enter、Escape 操作；抽屉、折叠区域和筛选面板必须可访问。
- 只在必要处使用 JS；服务端渲染页面在 JS 失败时仍能查看和提交核心表单。

## 9. 兼容性和数据要求

- 现有路由、POST action、查询参数名称和业务行为保持兼容。
- 桌面端宽度至少覆盖 1024px、1280px、1440px。
- 手机端至少覆盖 320px、360px、375px、390px、412px。
- 平板覆盖 768px × 1024px。
- 测试数据必须包含：长中文姓名、英文姓名、长地址、长银行描述、金额小数、空列表、匹配失败、错误提示和多条付款记录。
- 不允许用“空数据截图”作为移动端验收依据。

## 10. 验收标准

### 10.1 布局硬门槛

- 所有纳入范围的页面在 320/360/375/390/412px 下 `document.documentElement.scrollWidth === document.documentElement.clientWidth`。
- 不出现页面级横向滚动；如果保留历史表格横向滚动，必须只发生在明确标注的容器内。
- 核心业务页面在手机端不得出现宽表格或要求横向滑动；列表必须使用纵向卡片／分组内容完成主要任务。
- 页面首屏内容起点不因导航重复堆叠而超过 120px。
- 页面首次打开时，用户无需打开“更多筛选”即可看到当前最重要的待办或业务结论。
- 每个页面默认状态的主要动作不超过 1 个，次要动作不超过 2 个；其余动作必须折叠或进入菜单。
- 首屏不应同时出现超过 3 个同等级筛选控件。
- 任何可见文本、输入框、按钮、状态标签不得出现重叠、被裁切、逐字竖排或出现在不可到达的屏外位置。
- 手机端所有主要操作的真实点击命中区至少 44×44px。

### 10.2 业务操作门槛

- 月度总览：可切月、筛选状态、打开租客详情、展开付款明细、完成平账／催缴入口。
- 银行流水：可应用／清除筛选、分页、展开交易、完成匹配或归类、执行忽略／恢复／撤销。
- 租客管理：可添加、编辑、进入详情、查看历史、移除付款人关系。
- 支出：可录入并保存一笔支出，错误输入能在手机上正确显示。
- 现金收款：可填写、预览、确认入账；可打开作废页并提交原因。
- 所有操作后返回列表时，筛选和分页状态符合现有业务预期。

### 10.3 质量门槛

- `go test ./...` 全绿。
- 新增模板／布局回归测试，覆盖移动卡片结构、筛选展开、表单关键控件和桌面分支。

## 12. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 桌面表格和手机卡片维护两套模板导致数据展示漂移 | 先定义页面数据视图模型；共享状态、金额、标签和操作文案，视图只负责布局 |
| `/billing` 操作复杂，卡片展开后仍然过长 | 按状态分支显示动作；默认只显示当前状态允许的动作，拆分表单单独展开 |
| 服务端模板中重复写移动和桌面结构 | 先抽取可复用的模板片段和 CSS token，再分页面迁移 |
| 旧浏览器不支持部分 CSS | 核心查看和提交不依赖新 CSS；使用 `<details>`、普通表单和容器滚动作为降级 |
| 加大触控区域后页面变长 | 优先减少首屏次要字段，使用折叠详情，不单纯扩大所有元素的垂直间距 |
| 桌面端出现视觉回归 | 移动结构使用窄屏 media query；每个阶段跑桌面截图和现有 Go 测试 |
| 真机原生日期控件与 Chromium 表现不同 | 真实 iOS Safari／Android Chrome 做最终抽查，必要时统一显示格式但保留原生输入能力 |

## 13. 明确不做

- 不把所有表格永久改成卡片，桌面端仍保留表格效率。
- 不在本任务内做数据库迁移或业务规则重写。
- 不增加复杂前端框架，只为移动端引入 React 等新运行时。
- 不以“页面没有横向溢出”作为唯一成功标准；核心操作可见性、可点击性和数据完整性同样是阻断条件。
- 不把所有低频字段删除；低频字段应进入详情，而不是丢失。
- 不以“功能全部露出”为完整性标准；默认体验优先保障房东快速完成待办。

## 14. 待确认的产品决策

推荐方案是：**手机端对 `/billing`、`/rent-dashboard`、`/tenants`、`/expenses` 使用卡片摘要 + 就地展开详情；默认只展示待处理和高优先级内容；桌面端保留完整表格；筛选使用核心条件 + 更多筛选。**

这会比继续维护“手机横向滚动宽表”多一些模板工作，但能直接解决用户在手机上找不到操作、无法确认当前行身份、页面信息密度过高，以及房东需要自己判断下一步做什么的问题。
