# 技术设计：收租总览对齐

父任务 `design.md` 的架构与边界同样适用，此处只记录本子任务独有的决策。

## 1. 边界

改：`web/templates/pages/rent-workspace.html`、`web/static/css/pages/rent-workspace.css`、`rent_workspace.go` / `rent_workspace_page.go` 中的视图模型字段。

不改：账务计算、排序的业务口径、降级模板（`dashboard.go:210`）。

## 2. 关键决策

### 2.1 验收必须在有 DB 会话下进行

`/rent-dashboard` 有两条渲染路径：有 DB 会话 → `rent-workspace.html`；无 DB → `dashboard.go:210` 降级模板。**降级模板不是本次的对齐目标**（父任务 `design.md` §2.3）。

检查时若跑在没有 DB 会话的环境下，看到的会是降级模板，从而得出"改动没生效"或"结构还是旧的"这类错误结论。这是本子任务最可能出现的假阴性。

### 2.2 树形展开继续用 `<details>/<summary>`

父任务 `design.md` §2.5 已定：不引入 JS 状态管理。原生元素自带键盘可达性与 `aria-expanded`/`aria-controls` 语义，且现有实现已通过浏览器验证。

本子任务要做的是把现有的移动端 details 结构在 PC 表格上表达为原型的三级缩进（`tree-level-1` / `tree-level-2`）—— **这是样式工作，不是结构重写**。若在实现中发现必须重写结构才能表达，先记录再决定，不要直接推翻已验证的实现。

### 2.3 列合并的定序

用户已确认房产视角采用合并口径。合并后的列顺序需要定一个规则，否则十列会显得无组织：

建议按"对象 → 业务量 → 原型强调列 → 状态 → 操作"排列，即把收缴率与操作列追加在原有业务列之后，尽量不打断 PRD 已有的列顺序 —— 因为 PRD 列顺序有既有测试与用户认知依赖，原型列是新增项，追加比插入风险低。

### 2.4 统计 chips 的数据来源

原型 `dimensionSummary` 的四个 chips 是维度相关的：`本月共 N 套房产|间房|条租客责任`、`逾期未缴 N`、`部分缴纳 N`、`已缴满 N`。

这些应当**从当前维度已加载的数据聚合**，而不是新增后端查询 —— 页面已经为表格加载了这些行，chips 只是同一份数据的另一种呈现。新增查询会引入不一致的可能（chips 与表格数字对不上）。

### 2.5 平账入口排在 ④ 之后（已确认）

用户已确认本子任务**串行排在 ④ 之后**，而非并行。理由是平账表单归 ④ 定稿，两边各自实现会产生同一 action 的两个渲染点。

设计含义：

- 本子任务开工的前提是 ④ 已完成。开工前检查里这是一条硬门槛。
- 租客视角的「一键平账」渲染 ④ 定稿的那套表单，指向同一个 handler，不复制标记。
- 页面上平账入口是**行内展开**（`<details>/<summary>`）而非跳转 —— 与 `/bills` 现有做法一致（`rent_collection_pages.go:49`）。跳转会让用户离开总览页，破坏三视角的浏览动线。
- 表单需要带回列表上下文（`period` / `search` / `status` / `sort` / `page` / `page_size`）时，按 ④ 的字段集照搬；收租总览的对应上下文取自当前视角与筛选状态。

代价（显式接受）：本子任务不再与 ②④⑤ 并行，整体完工时间后移。换来的是平账表单只有一处定义。

## 3. 兼容与回滚

- 排序口径、筛选上下文、detail-return 链路是既有契约，改动时不得破坏。
- 独立提交，可单独 revert。

## 4. 验收方式

- 在有 DB 会话的条件下渲染并截图（见 §2.1）。
- 三个视角（房产/房间/租客）各截一次 —— 只截默认视角会漏掉两个视角的列改动。
- 四档宽度，断言 `scrollWidth === clientWidth`。
