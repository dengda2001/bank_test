# 技术设计：列表页对齐

父任务 `design.md` 的架构与边界同样适用，此处只记录本子任务独有的决策。

## 1. 边界

改：十个列表页模板与对应 `pages/*.css`；`rent_collection_pages.go` / `page_data_routes.go` 等内联字符串模板的页面。

不改：路由契约、表单字段名、action URL、账务计算。

注意：`page_data_routes.go` 与 `rent_collection_pages.go` 是**内联字符串模板，无编译期检查** —— 改错不会编译失败，只会在运行时渲染出坏页面。改动后必须实机渲染该页。

## 2. 关键决策

### 2.1 filterbar 控件必须真实有效

父任务 A1 的硬约束：不得做无行为的假控件。这条对本子任务尤其关键 —— 十个页面结构"统一"最省事的做法就是复制同一段 filterbar，但多数页面并没有那么多个筛选维度。

规则：**渲染该页真实具备的筛选控件**。无月份维度的页面不渲染月份下拉。为凑齐十页一致而渲染的无效下拉，正是 A1 禁止的。

（父任务原验收项写的是"十页均具备……月份下拉"。用户已确认按本节的实质约束执行，父任务对应验收项已同步改为「每页具备其数据支撑的筛选控件」。）

### 2.2 平账表单：加字段，不改契约

现状：`rent_collection_pages.go:49-50` 的表单字段为 `obligation_id` / `period` / `search` / `status` / `sort` / `page` / `page_size` / `reason`，POST 到 `/bills/settle` → `handleDashboardManualBalance`。

原则：**新增字段，不改变已有字段名与 action**。已有字段名有服务端处理器与测试依赖，改名会连带改动 handler。

「处理方式」是本子任务唯一引入新语义的字段。父任务 `design.md` §2.6 已定：**只启用「匹配现有收款」**（与当前行为等价），其余三项渲染为可选但提交时返回明确的未实现提示。

这样做的理由：表单结构对齐原型，但不静默引入未经确认的账务规则。「登记减免」「结转下月」涉及账务口径，超出 UI 对齐的性质。

### 2.3 「生成本月账单」改为显式动作

现状是自链接（`rent_collection_pages.go:45`），靠 GET 隐式幂等触发（`obligations.go:353`）。

改为显式动作时有两个约束：

- **幂等性必须保持** —— 重复触发不得产生重复账单。这是现有 GET 隐式行为已保证的，改成显式动作不能丢掉。
- 若改为 POST，需确认不破坏 `responsive-conventions.md:209-214` 的 detail-return 上下文契约。

建议保留幂等语义，只把入口从"自链接"改成"触发动作"，不改变其幂等实现。

### 2.4 两处已确认缺陷的修复

- `rooms.html:61`：`<small>自 {{.ActiveFrom}}</small>` 在 `ActiveFrom` 为空时渲染孤立「自」字。修法是把整个 `<small>` 纳入条件，而不是只对空值做占位。
- `/bills` 也有两套渲染路径（`dashboard.go:168-174` 按 URL 分派）。`/bills` 恒定命中 `rent_collection_pages.go:42`，因此以它为准。

## 3. 兼容与回滚

筛选/排序/分页/detail-return 上下文是既有契约，有测试与浏览器验证覆盖，**改动时不得破坏**。每个页面独立提交。

## 4. 验收方式

- 十个页面各自实机渲染截图，四档宽度。
- 每个 filterbar 控件实际提交一次，确认过滤生效。
- 断言 `scrollWidth === clientWidth`。
- 平账表单分别提交「匹配现有收款」（应生效）与其余三项（应给出未实现提示且无账务副作用）。
